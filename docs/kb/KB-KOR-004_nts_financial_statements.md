# KB-KOR-004: 국세청 표준재무제표 리포트

## 1. 요약

법인세법 §60② 는 **모든 법인**이 법인세 신고 시 표준재무상태표·표준손익계산서(제조업은 제조원가명세서 포함)를 제출하도록 합니다. [KB-KOR-002](./KB-KOR-002_korean_chart_of_accounts.md) 가 만든 계정↔서식코드 매핑을 실제로 소비해 서식 형태로 출력하는 것이 이 리포트입니다.

| 산출물 | 위치 (형제 앱 저장소) |
|---|---|
| 엔진 | `setive_erpnext_kr/korea/common/nts_report.py` |
| 서식 행 정의 | `setive_erpnext_kr/korea/common/data/nts_form_rows.json` (bs 287 · is 199 · mfg 45행) |
| 리포트 3종 | `setive_erpnext_kr/setive_erpnext_kr/report/nts_standard_{balance_sheet,income_statement}/`, `.../nts_manufacturing_cost_statement/` |
| 검증 fixture | `scripts/nts/fixture_company.py` — 제조·상품매매 회사를 만들고 지운다 (§7) |

포크는 수정하지 않았습니다.

## 2. 자료 흐름

```
계정과목표 (포크 verified/kr_*.json)
   └→ 회사 생성 시 Account 324개
        └→ nts_codes.apply()  ─── 매핑표(nts_standard_code_map.json)를 읽어
             Account Custom Field(setive_nts_{bs,is,mfg}_code / role) 에 기록
                  └→ nts_report 엔진이 **Custom Field 를 권위로** 읽음
                       + 행 구조는 nts_form_rows.json
                       + 집합·산식·대사는 nts_standard_code_map.json
                            └→ Script Report 3종
```

**권위가 분할**된 것이 핵심입니다. 계정 배정은 Custom Field 라서 테넌트가 손으로 재매핑한 것이 보존되고(`apply(force=False)` 가 빈 계정만 채움), 행 구조·산식·엔진 동작 설정은 파일이 권위입니다. 네 축의 목록은 §3 끝의 표에 있습니다.

> ⚠️ **매핑표(JSON)를 고쳐도 리포트는 바뀌지 않습니다.** 엔진은 Custom Field 를 읽습니다. 매핑을 바꿨으면 `nts_codes.apply(company, force=True)` 로 계정에 다시 밀어넣어야 합니다. 실측에서 이걸 빠뜨려 매출원가가 0 으로 나왔습니다.

## 3. 계산 규격

`computed_ops` 7종으로 서식 행을 계산합니다.

| op | 뜻 |
|---|---|
| `opening_balance` / `closing_balance` | 기초·기말 잔액 합 |
| `movement` | 기간 발생액. 라인마다 **상대계정**을 구해 `except_counter` 집합이면 제외(재고 내부이동·원가대체 배제). 상대계정 판정은 §4 |
| `formula` | 같은 서식 행 코드와 `direct`(그 행에 직접 배정된 계정 잔액) 의 사칙연산 |
| `ref` | 다른 서식 행 참조 (is 44 → mfg 49) |
| `children` | 자식 행 합계 |
| `constant` | 대응 계정이 없는 행 |

행 속성 `contra`(괄호 항목)는 상위 합계에 음수로 들어갑니다. `level:"parent"` 는 하위 내역 행을 쓰지 않고 **총계 행에 원장을 직접 배정**한다는 뜻입니다.

`role` 은 배정에서 제외합니다 — `reconcile_only`(대사에만 사용), `not_applicable`.

매핑표를 고치지 않고 엔진 상수로 얹는 보정은 `nts_report.py` 모듈 docstring의 **D-1 ~ D-6** 입니다. 적용 사실은 매 실행 `spec_patch` 등급 info 경고에 남습니다.

**D-7(원재료 타계정대체)만은 엔진 상수가 아니라 매핑표 설정입니다** — 세무 판단이 갈리는 지점이라 테넌트가 고를 수 있어야 하기 때문입니다(§4.4). 그래서 권위 축이 하나 늘었습니다.

| 대상 | 권위 |
|---|---|
| 계정 → 서식 행 배정 · role | Account Custom Field `setive_nts_*` |
| 서식 행 구조 | `data/nts_form_rows.json` |
| 집합 · 산식 · 대사 | `data/nts_standard_code_map.json` |
| **엔진 동작 설정(세무 판단 분기)** | **`data/nts_standard_code_map.json` 의 `meta.options`** |

## 4. 영구재고와 실지재고 산식 — 상대계정은 `against` 로 판정한다

### 4.1 문제

ERPNext 는 **영구재고**라 판매 시점에 실제 매출원가를 원장(`5110` 상품매출원가 · `5120` 제품매출원가)에 계상합니다. 서식의 매출원가 블록은 **실지재고 방식**입니다.

```
(1)상품매출원가 36 = 기초재고 37 + 당기매입원가 38 − 관세환급 39 − 기말재고 40 − 타계정대체 41
(2)제조원가    42 = 기초재고 43 + 당기총원가 44 − 관세환급 45 − 기말재고 46 − 타계정대체 47
                     (44 = 제조원가명세서 49 당기제품제조원가, 서식 작성방법 제3항이 일치를 강제)
```

이 등식은 재고계정의 T계정 항등식이라 **측정만 맞으면 원장과 정확히 같아야** 합니다. 기초·기말은 잔액이므로 신뢰할 수 있고, 유입(38·mfg 3)과 타계정대체(41·47·mfg 48)만 `movement` 로 잽니다.

2026-09-07 실측(데모 회사)에서 산식 39,928 vs 원장 253,760 이 나왔고, 당시에는 총계 행을 원장으로 덮는 엔진 상수(`COGS_DIRECT`)로 우회했습니다. 그 우회는 잘못이었습니다 — 원인을 잘못 짚었고 새 결함을 만들었습니다(§9).

### 4.2 진짜 원인 — 상대계정 비례 배분

옛 엔진은 상대계정을 **전표 안 반대편 라인에 금액 비례로 배분**해 구했습니다. ERPNext 는 `Sales Invoice(update_stock=1)` 한 전표에 수익 분개(1131/4111)와 원가 분개(1152/5120)를 함께 싣습니다(`erpnext/accounts/doctype/sales_invoice/sales_invoice.py` — `gl_entries += super().get_gl_entries()`). 그래서 재고 대변 4,500 의 상대가 매출채권 69%·원가계정 31% 로 쪼개졌고,

- `counter_in_reverse: SETTLEMENT`(매입환출 화이트리스트)에 매출채권이 들어 있어 **외상매출 전표마다 당기매입원가가 깎였습니다.** 상품매매 fixture: `is 38` 110,000 이 80,000 으로(40,000 × 0.75 누락).
- 매출채권 몫이 타계정대체로 새어 산식 총계가 원장의 43% 만 인쇄됐습니다(데모 실측 109,822 vs 253,760).

### 4.3 정정 — D-6

재고 GL 라인의 `GL Entry.against` 는 코어가 **상대계정을 직접 써 넣습니다**: `erpnext/controllers/stock_controller.py` `get_gl_entries` 가 창고 leg 의 `against = expense_account`(target_warehouse 가 있으면 그 창고 계정) 로 만듭니다. Purchase Invoice 계열만 `against = self.supplier`(거래처명)입니다(`erpnext/accounts/doctype/purchase_invoice/purchase_invoice.py`).

엔진 `_exact_counter` 규칙:

| `against` | 상대계정 |
|---|---|
| 이 회사 계정 하나 | 그 계정 |
| 계정이 아닌 단일 토큰(거래처명) | `PARTY` — SETTLEMENT 집합의 원소로 취급(매입·매입환출) |
| 계정 여러 개(Journal Entry) · 빈 값 · 자기 계정 | 비례 배분으로 폴백 + `counter_fallback` 경고 (등급은 §6.1) |

폴백 경고는 **배분 비율이 서식 값을 바꾸는 전표만** `warning` 으로 올립니다. 판정 기준은 `_fallback_partitions` 입니다 — movement 이 상대계정을 보는 방법은 `excl`(자기 집합 ∪ `except_counter`) 밖인가와 `counter_in_reverse` 안인가 둘뿐이므로, 어떤 구분선도 배분 대상 계정들을 가르지 않으면 비율을 어떻게 바꿔도 모든 행의 값이 같습니다. 그런 전표는 `info` 로 내려 리포트 화면을 채우지 않습니다. 메시지에는 전표 번호·대상 계정 줄·배분 금액·사유·권장 조치가 들어갑니다(§6.1).

**재고계정 Journal Entry 는 막혀 있지 않습니다 — 조건부입니다.** `journal_entry.py` `validate_stock_accounts` 는 `account_type="Stock"` 인 계정에 대해 해당 시점의 **GL 계정잔액과 재고원장 잔액이 같을 때만** `StockAccountInvalidTransaction` 을 던집니다(`erpnext/accounts/doctype/journal_entry/journal_entry.py:360-378`, 비교 대상 산출은 `erpnext/accounts/utils.py:1873-1907`). 두 값이 다르면 통과합니다. 특히 **어느 창고에도 매여 있지 않은 재고계정**(제조 프로필의 1151·1153·1156·1157)은 `related_warehouses` 가 비어 회사 전체 재고가치와 비교되므로 사실상 항상 통과합니다(`get_stock_value_on` 은 창고 목록이 비면 필터를 걸지 않습니다 — `erpnext/stock/utils.py:59-90`). 제조 fixture 가 이 경로로 1156 부재료에 JE 2건을 넣습니다 — 단일 상대계정 매입(폴백 없음)과 정상·비정상 감모가 섞인 실사차이(폴백 warning)입니다. 폴백 info 는 다계정 임금 JE 가 냅니다(§7.1).

이 규칙만으로 상품매매 fixture 의 `is 36` 이 `기초 0 + 유입 110,000 − 기말 37,300 − 타계정대체 3,000 = 69,700` 으로 원장(5110 68,000 + 감모 1,000 + 평가손실 700)과 **1원까지 일치**합니다. 플러그가 필요 없습니다. `COGS_DIRECT` 는 삭제했고 매핑표의 `5110`·`5120` 은 원래대로 `reconcile_only` 입니다.

### 4.4 원재료의 타계정대체 — D-7 (매핑표 설정)

법인세 제조원가명세서의 재료비 블록(mfg 1~4)에는 타계정대체 행이 없습니다(소득세 서식에는 있음). 원재료를 견본비·건설중인자산 등으로 대체하면 `재료비 = 기초 + 매입 − 기말` 이 그만큼 과대계상되고 당기총제조비용(44)·당기제품제조원가(49)·손익계산서 44 까지 번져 매출원가 항등식이 실패합니다.

처리 방법이 둘이고 **어느 쪽이 맞는지는 세무 판단**입니다. 그래서 코드 상수가 아니라 매핑표 설정으로 고릅니다.

```json
"meta": { "options": { "rm_other_transfer": { "value": "mfg48", "allowed": ["mfg48", "mfg3"] } } }
```

| 값 | 처리 | 재료비(1) · 당기총제조비용(44) | 당기재료매입액(3) | 타계정대체액(48) |
|---|---|---|---|---|
| `mfg48` (기본) | Ⅷ.타계정대체액(48)에 합산 | 투입 전 총액(대체액 포함) | **실매입액 그대로** | 재공품분 + 원재료분 |
| `mfg3` | 당기재료매입액(3)에서 차감 | 대체액을 뺀 값 | 실매입액 − 대체액 | 재공품분만 |

**두 모드의 차감 기준식이 같으므로 당기제품제조원가(49)는 항상 일치합니다.** `49 = 44 + 45 − 47 − 48` 에서 `mfg48` 은 44 와 48 에 같은 금액 T 를 더하고 `mfg3` 은 둘 다 더하지 않으므로 T 가 상쇄됩니다. 서식 작성방법 제3항이 강제하는 `mfg 49 == is 44` 와 매출원가 항등식은 어느 모드에서도 성립합니다(§7.2 실측).

기본값을 `mfg48` 로 둔 근거: 당기재료매입액(3)은 **매입 세금계산서 합계·지출증명서류 수취명세서와 대조되는 행**이라 실매입액을 유지해야 하고, 48 은 "제조원가 중 제품이 되지 않은 것" 이라는 뜻에 맞습니다. 이 선택은 세무 검토 대상입니다(§10).

`mfg3` 을 고르면 차감액이 있는 산출마다 `rm_transfer_mode` **warning** 경고가 납니다 — 차감액과 "이 행은 실매입액이 아니므로 매입 세금계산서 합계와 그만큼 어긋난다"는 문구가 함께 나갑니다(차감할 것이 없으면 조용합니다). 조용한 오류가 되지 않게 하려는 장치입니다.

전환 절차:

```bash
# 형제 앱 저장소(setive_erpnext_kr) 루트에서 실행한다. 포크 경로는 ../setive-oss-erpnext-16.33 이다.
CHART=../setive-oss-erpnext-16.33/erpnext/accounts/doctype/account/chart_of_accounts/verified/kr_standard_chart_of_accounts.json

# 1. 생성기를 고친다 (JSON 은 생성물이라 손으로 고치면 다음 재생성에서 사라진다)
#    scripts/coa/build_nts_map.py 의 OPTIONS["rm_other_transfer"]["value"] = "mfg3"
python3 scripts/coa/build_nts_map.py

# 2. 정적 검증 — 기대: errors 0, warnings 0
python3 scripts/coa/validate_coa.py "$CHART" \
  --map setive_erpnext_kr/korea/common/data/nts_standard_code_map.json --nts scripts/coa/nts_codes.json

# 3. 앱 서비스를 재시작한다 — 계정 배정이 아니라 산식이므로 nts_codes.apply 재실행은 필요 없다
```

`validate_coa.py` 는 허용값과 `schema_version` 을 **엔진 소스에서 읽어**(`engine_contract()`) 대조합니다. 엔진이 모르는 값·오타 난 설정명·설정 누락이 전부 errors 로 잡히므로, 이 단계를 건너뛰지 않으면 잘못된 설정으로 서식이 인쇄되는 일은 없습니다.

되돌리려면 같은 절차로 `"mfg48"` 을 쓰면 됩니다. 구현은 `nts_report.RM_TRANSFER_PATCH` 이며, 엔진이 모르는 값이 들어오면 `load_map` 과 리포트가 즉시 throw 합니다(조용히 기본값으로 돌지 않습니다).

### 4.5 블록 흐름 진단

정확한 상대계정이 생기자 "장부가 서식 블록 구조에 맞지 않는" 경우를 짚을 수 있게 됐습니다. `_check_block_flows` 가 error 등급 `block_flow_mismatch` 로 알립니다.

- 재고계정에서 그 블록이 아닌 원가계정으로 대체 (예: 재공품 1154 → 5120, 원재료 1155 → 5120)
- 제품·재공품 계정으로 직접 매입 (서식 제조원가 블록에는 매입 행이 없다)

이 경고가 나오면 회계가 아니라 **창고→계정 매핑이 업종과 어긋난** 것입니다. 데모 회사가 정확히 이 상태입니다(§7.3). 고치는 방법이 §4.6 입니다.

## 5. 대사(reconciliation)

`reconcile(company, fiscal_year)` 가 9개 식을 평가합니다. 리포트가 스스로를 검증하는 장치이며, 2026-09-07 결함도 2026-09-08 결함도 **사람보다 먼저 잡아냈습니다.**

| 식 | 내용 |
|---|---|
| 매출원가 항등식 | `assigned(is.35)+gl(5110)+gl(5120)+gl(5140)+gl(5141)+gl(5150)+net(MFG_COST) == is.35` — 원장 대 산식의 독립 검산. `assigned(is.35)` 는 매출원가 아래 계정을 직접 붙이는 블록(공사·운송·임대·분양·지분법·기타 — 5130 포함)의 원장 합. 잔액 산식 블록(36·42)은 건너뛰고 `gl()`/`net()` 이 센다. 기말재고·타계정대체 같은 (−) 행(is 51·52·58·59·64·65)에 붙인 계정은 `sign_in_parent` 를 반영해 음수로 센다 — 우변 `_children_sum` 과 같은 규칙 |
| 제조원가명세서-손익계산서 연결 | `mfg.49 == is.44` (ref 라 구성상 항등 — 서식 작성방법 제3항) |
| 재고자산 재무상태표 대사 | `bs.44 == closing_balance(INV_ALL)` |
| 결산대체 완료 | `gl(5422)=gl(5423)=gl(5452)=0` (단일 손익계정, KB-KOR-002 §9-3) |
| 대차평균 | `bs.228 == bs.383` |
| 완전성 4종 | 자산·부채·자본 총계와 당기순손익이 GL 과 일치 |

`매출원가 항등식` 의 `assigned(is.35)` 는 2026-09-08 에 `gl(5130)` 을 일반화한 것입니다. 이전에는 5130 밖의 매출원가 계정(테넌트가 추가한 공사원가 등)이 항등식에서 빠져 구조적으로 실패했습니다. 상품매매 fixture 가 테넌트 추가 `5160 공사원가`(→ is 50) 2,000 으로 검증합니다.

`완전성 — 자본총계` 의 우변은 **GL 손익**(`Equity + (Income − Expense)`, 결산 후엔 `Equity`)입니다. 이전에는 좌변과 같은 `is.219` 를 넣어 항상 상쇄되는 공허한 검산이었습니다(§9).

허용오차는 절대 1원(`RECON_ABS_TOL`)입니다. 매핑표가 제안한 0.5% 상대오차는 10억 재무상태표에서 500만원을 통과시켜 검산이 무의미해지므로 좁혔습니다.

결산 전(가결산)에는 `is.219` 가 `bs.382` 에 임시 가산되므로 손익 결함이 대차평균·자본총계까지 번집니다. 결산분개(PCV) 후에는 매출원가 항등식·당기순손익 완전성 두 식만 반응합니다.

### 5.1 왜 5141 은 5460 처럼 분리하지 않는가

`매출원가 항등식` 이 `gl(5140) + gl(5141)` 을 원장 항으로 세는 이유, 그리고 감모손실은 정상(5140)·비정상(5460)으로 **계정을 나누는데** 평가손실(5141)은 나누지 않는 이유입니다. 다음 사람이 같은 질문을 반복하지 않도록 남깁니다.

| | 재고자산감모손실 | 재고자산평가손실 |
|---|---|---|
| 상대계정 | **재고계정 자체**(1151~1158) — 재고가 물리적으로 줄어든다 | **평가충당금**(1161~1164) — 재고 수량은 그대로고 순액만 준다 |
| 서식 영업외비용 행 | **있다** — is 188 `6.재고자산감모손실` | **없다** — 영업외비용(is 179)의 직계 자식 21개(후손 33개) 어디에도 재고자산평가손실 행이 없다. 평가손실 계열은 is 187 단기투자자산평가손실(5440)·is 196 파생상품평가손실뿐 |
| 비정상분 분리 | 계정을 나눠 5460 → is 188 로 직접 배정 | **배정할 행이 없어 계정을 나눠도 실을 곳이 없다** |

즉 5141 을 5460 처럼 다루려면 "비정상 재고자산평가손실" 을 실을 서식 행이 필요한데 **법인세 표준손익계산서에 그 행이 없습니다**. 계정만 신설하고 코드를 비워 두면 엔진의 미매핑 라우팅이 계정 트리를 타고 올라가 영업외비용 '기타'(is 212)로 보내고 `unmapped_routed` **warning** 을 남깁니다 — 값은 영업외비용에 실리지만 서식상 근거가 없는 배정이고, 감모손실처럼 전용 행에 대응하는 것과는 다릅니다. 따라서 **5141 은 현행대로 `reconcile_only` 로 두고 평가충당금이 기말재고를 줄여 매출원가에 흡수되게 합니다.** 저가법 평가손실을 매출원가로 보는 일반기업회계기준 관행과도 일치합니다.

다만 "비경상적으로 큰 평가손실을 영업외비용으로 볼 여지가 있는가" 는 회계·세무 판단이므로 §10 검토 목록에 올립니다. 이 결론이 바뀌면 [ONT-ENT-001](../ontology/ONT-ENT-001_inventory_cost_flow.md) §2.4 표와 §7.3 도 함께 고쳐야 합니다.

## 6. 사용법

Report 3종은 Script Report 로 등록되며 `install.py` 의 `after_install`/`after_migrate` 가 멱등하게 보장합니다. `bench migrate` 를 쓸 수 없는 개발 환경에서는 직접 호출합니다.

```bash
bench --site <site> execute setive_erpnext_kr.korea.common.nts_report.install_reports
```

필터는 회사·회계연도이며, 데스크에서 리포트 이름으로 엽니다(`NTS Standard Balance Sheet` 등).

미매핑 원장은 `ROOT_FALLBACK` 으로 루트별 '기타' 행에 라우팅하고 **error 등급 경고**를 남깁니다(유동/비유동을 뒤집을 수 있으므로). 점검은 `nts_codes.report_unmapped(company)`.

`report_unmapped` 는 세 가지를 함께 돌려줍니다 — `unmapped`(코드가 비어 배정되지 않은 원장) · `missing`(**매핑표에는 있는데 회사에 없는 계정번호**) · `stale`(회사에 박힌 서식 개정 표식이 매핑표와 다름). `missing` 은 계정과목표에 계정이 추가된 뒤 생긴 격차를 잡습니다 — 계정 신설은 코어 `create_charts` 가 **회사 생성 시점에만** 돌기 때문에 그 전에 만들어진 회사에는 새 계정이 없습니다(§8-4).

### 6.1 경고 등급과 조치 — 운영 가이드

경고는 `level` 3단(`error` · `warning` · `info`)이며 **리포트 화면에는 error·warning 만** 나옵니다. 표출 상한은 건수가 아니라 **줄 수**(16줄)입니다 — 폴백 경고 하나가 전표 내역으로 여러 줄을 만들기 때문이며, 잘린 건수는 마지막 줄에 표시됩니다. `info` 를 포함한 전량은 `reconcile()` 응답에서 봅니다.

```bash
bench --site <site> execute setive_erpnext_kr.korea.common.nts_report.reconcile \
  --kwargs "{'company':'<회사명>','fiscal_year':'2026'}"
```

| 등급 | 뜻 | 대응 |
|---|---|---|
| `error` | 서식 값이 틀렸거나 틀릴 수 있다 | **제출 전에 반드시 고친다** |
| `warning` | 값은 나왔으나 전제를 사람이 확인해야 한다 | 확인 후 판단 |
| `info` | 설정·상태 기록 | 감사 추적용. 조치 없음 |

자주 보게 되는 것만 추립니다.

| 코드 | 등급 | 언제 | 조치 |
|---|---|---|---|
| `counter_fallback` | warning | 상대계정을 확정하지 못했고 **배분 비율이 서식 값을 바꿀 수 있다** | 아래 §6.1.1 |
| `counter_fallback` | info | 상대계정을 확정하지 못했으나 **어떤 비율이든 같은 값** | 없음 |
| `block_flow_mismatch` | error | 재고 흐름이 서식 블록 구조와 어긋난다 | 창고→계정 매핑을 업종에 맞춘다(§4.6) |
| `unmapped_routed` | warning (루트 폴백이면 error) | 배정되지 않은 원장을 계정 트리로 추정 배정했다. 루트별 '기타' 까지 밀리면 error — 유동/비유동을 뒤집을 수 있다 | `report_unmapped` 로 확인 후 Account 에 코드를 넣는다 |
| `unmapped_unroutable` | error | 배정할 행을 아예 찾지 못했다 | 위와 같음 |
| `rm_transfer_mode` | warning | D-7 설정이 `mfg3` 라 당기재료매입액을 깎았다(차감액이 있을 때만) | 의도한 설정인지 확인(§4.4) |
| `negative_purchase` | error | 타계정대체액이 매입액을 넘어 당기재료매입액이 음수다 | 전표 상대계정을 확인한다 |
| `unclosed_pl` | warning | 결산분개(PCV) 전 산출 | 제출용은 PCV 후에 뽑는다 |
| `spec_patch` | info | 엔진 보정 D-1~D-6 과 D-7 설정값 기록 | 없음 |
| `form_revision` | warning | 산출 연도가 매핑표 적용 시작 사업연도보다 이르다 | §8-2 |

서식 개정 표식 불일치(`stale`)는 경고가 아니라 `report_unmapped(company)` 응답의 키다 — 리포트 실행이 아니라 점검으로 확인합니다(§6).

#### 6.1.1 `counter_fallback` — 무시해도 되는 경우와 고쳐야 하는 경우

엔진은 재고·제조원가 라인의 상대계정을 `GL Entry.against` 로 판정합니다(§4.3). Journal Entry 는 반대편 계정을 **쉼표로 모두** 적으므로 상대가 하나로 특정되지 않고, 그때만 옛 방식(금액 비례 배분)으로 내려갑니다.

**무시해도 되는 경우 (info)** — 배분 대상 계정들이 모든 산식에서 같은 취급을 받을 때. 대표적으로 **다계정 결제 JE**(임금을 현금·예금에서 나눠 지급 등)입니다. 상대가 전부 결제계정이라 매입액·타계정대체액 어느 산식도 이들을 가르지 않아, 비율을 어떻게 잡아도 값이 같습니다. 정상 업무에서 늘 생기므로 화면에 띄우지 않습니다.

**반드시 확인해야 하는 경우 (warning)** — 배분 대상 계정이 산식의 제외 집합 **안팎에 걸쳐 있을 때**. 예를 들어 재고 대변의 상대가 `5140 재고자산감모손실`(정상 — `COGS_ADJ` 라 타계정대체에서 제외)과 `5460 재고자산감모손실(비정상)`(제외 안 됨)로 섞이면, 엔진이 정한 비율이 곧 타계정대체액(mfg 48)이 됩니다. 금액 비례가 실제 배분과 다르면 **서식 값이 그만큼 틀립니다.**

판정은 `_fallback_partitions` 가 모은 구분선으로 합니다 — movement 행의 제외 집합·역방향 화이트리스트, D-2 흡수 전 측정이 쓰는 계정별 제외 집합, 블록 흐름 진단의 COGS 세분(5110·5120), 매입 판정의 거래처. **보수적으로 기울여 두었습니다**: 갈리는 구분선이 있으면 값이 실제로 바뀌지 않는 경우에도 warning 을 올립니다. 빠뜨려서 조용히 info 로 내려보내는 것보다 한 번 더 확인받는 편이 낫기 때문입니다.

경고 메시지에 전표 번호·대상 계정 줄·배분 금액·사유·권장 조치가 들어갑니다. 실제 출력:

```
• 상대계정을 확정하지 못해 금액 비례로 배분한 전표 1건입니다. 배분된 상대계정이 산식의 제외 집합
  안팎에 걸쳐 있어 비율이 실제 귀속과 다르면 서식 값이 그만큼 틀립니다 — 아래 배분이 맞는지 확인하십시오.
    ▸ Journal Entry ACC-JV-2026-00036 — 1156 대변 5,000 → 5140 3,000, 5460 2,000
      [against 에 계정이 2개 이상 나열됨 — Journal Entry 는 반대편 계정을 전부 적는다]
    · 조치: 재고 전표(Stock Entry·Stock Reconciliation)로 다시 기표하면 코어가 상대계정을 한 개로
      써 넣습니다. Journal Entry 로 남겨야 하면 상대계정이 하나가 되도록 전표를 나누십시오(성격별 1건씩).
```

조치는 사유별로 다릅니다.

| 사유 | 뜻 | 권장 조치 |
|---|---|---|
| against 에 계정이 2개 이상 | Journal Entry 의 쉼표 나열 | 재고 전표로 재기표하거나, 상대계정이 하나가 되도록 전표를 성격별로 나눈다 |
| against 가 비어 있음 | 상대계정이 기록되지 않았다 | 전표를 취소 후 재기표한다 |
| against 가 자기 계정 | GL 병합으로 상대가 유실됐다(§8-7) | 원가중심·프로젝트를 지정하거나 전표를 나눈다 |

**상대계정이 하나인 전표는 애초에 폴백을 타지 않아 경고가 없습니다** — 기초잔액 이관처럼 단일 상대계정으로 기표한 재고계정 JE 는 아무 경고도 내지 않습니다(제조 fixture 가 이 경우를 검증합니다).

## 7. 검증

### 7.1 fixture 회사

데모 회사(`세티브 (Demo)`)는 **검증에 쓸 수 없습니다**(§7.3). 대신 회계적으로 유효한 흐름을 가진 회사 두 개를 스크립트로 만듭니다.

- **폴백 구분선(`_fallback_partitions`)이 불완전했습니다.** 초안은 movement 행의 제외 집합과 COGS·INV_ALL·거래처만 넣었는데, 엔진에는 술어가 둘 더 있습니다 — D-2 흡수 전 측정은 제외 집합이 `{그 계정} ∪ INV_ALL` 이라 **계정마다 다르고**, 블록 흐름 진단은 `COGS 안이면서 그 재고집합의 허용 원가계정이 아닌가` 라 **재고계정마다 다릅니다**. 빠진 술어 탓에 제조간접비끼리 얽힌 폴백과 COGS 내부(5110/5120)로 갈리는 폴백이 "조치할 것 없음(info)" 으로 내려갔습니다. 싱글턴 구분선을 넣어 고쳤고, 판정은 이제 과검출 쪽으로 기울어 있습니다(§6.1.1).
