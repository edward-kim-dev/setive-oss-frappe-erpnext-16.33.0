# KB-KOR-005: 한국 현지화 로드맵 — 다음 구현 꼭지 선정 근거

## 1. 요약

2026-09 기준 SETIVE 한국화는 **"결산 산출물" 한 축만** 깊게 구현돼 있다. 거래 발생 → 증빙 → 신고로 이어지는 앞단이 비어 있다.

```
   [거래]  →  [증빙]        →  [신고]        →  [결산]
     △          없음            없음            ✅ 구현됨
   전표 축      전자세금계산서    부가세 신고서    KR COA · Company 훅
   없음                          합계표          국세청 표준재무제표 3종
```

**다음 목적지는 전자세금계산서다.** 다만 발급 기능부터 만들지 않고, 그 밑에 깔릴 **세무 마스터 계층**을 1차로 놓는다. 세금계산서 XML 이 요구하는 대표자성명·업태·종목이 ERPNext `Customer`/`Supplier` 에 존재하지 않아, 이 필드 없이 발급을 만들면 기존 거래처 전량이 "발급 불가"로 시작한다.

| 차수 | 범위 | 외부 비용 | 결론 근거 |
|---|---|---|---|
| **1차** | 세무 마스터 계층 + 팝빌 샌드박스 스파이크 | 0원 | 2개 심사 관점 **합의** |
| 2차 | (분기) 전자세금계산서 발급 **또는** 홈택스 자료수집+부가세 신고 | 협의 단가 | 심사 **갈림** — §5 |
| 3차 | 나머지 한쪽 + 법정 인쇄양식 | | |

## 3. 선정 과정

렌즈 3개로 독립 제안을 만들고 2개 관점으로 심사했다.

| 렌즈 | 제안 | 아키텍트 | 세무실무 |
|---|---|---|---|
| A 도입장벽 | 전자세금계산서 완결 (마스터~인쇄양식) | 36 | 38 |
| B 리스크선행 | 전자세금계산서 수직 슬라이스 (샌드박스 1건) | **43** | 40 |
| C 복리 | 세무 마스터 계층 (신원 필드·전표 축·설정 골격) | 40 | **41** |

승자가 갈렸으나 **두 심사자의 1차 권고는 동일하다** — C 를 축으로 하되 B 의 무료 스파이크를 병렬로 돌린다.

### 3.1 각 관점이 상대를 꺾은 논거

**아키텍트가 A 를 감점한 이유**: 마스터데이터 → 자격증명 → PoC 순서라, "틀리면 설계를 뒤엎는 사실"(컨테이너 egress 가능 여부, SDK 의 RQ 멀티프로세스 안전성)이 5~7주차에야 드러난다. 중간 출하물 없이 ~20주를 통짜로 커밋한다.

**세무실무가 B 를 감점한 이유**: 수정세금계산서·계산서(면세)·월합계를 전부 제외하고 "발급취소"만 지원하는데, ASP 는 통상 익일 전송이라 **취소 가능 구간이 사실상 당일뿐**이고 전송 후에는 수정발행이 유일한 경로다. 반품·단가조정·계약해제는 월 단위로 반드시 발생하므로 이 범위가 끝나도 실무 투입이 불가능하다.

**양쪽이 C 를 1차로 인정한 이유**: A·B 의 첫 두 마일스톤이 곧 C 이고, 외부 계약 0·포크 수정 0·3~5주로 끝난다.

### 4.2 심사가 지적한 설계 정정 (착수 시 반영)

| 항목 | 초안 | 정정 |
|---|---|---|
| 전표 축 기본 정책 | 경고(warn) | **기본값 강제 세팅 + 예외만 선택**. 경고만 뜨는 분류 필드는 실무에서 예외 없이 무시된다 |
| 불공제 8버킷 | 전부 전표 Select | ①필요적 기재사항 누락 ⑤면세사업 관련 ⑦사업자등록 전 은 **입력 시점에 사람이 알 수 없다**. ⑤는 과세기간 말 안분 계산의 **산출물**이다(별지 제22호서식 2번 표). 전표 Select 에는 ②③④⑥⑧만 |
| 국세청 서비스키 | SETIVE 공통 키 폴백 | **테넌트별 키를 기본**, 공통 키는 옵트인 폴백. 1일 100만건 한도가 한 계정에 묶여 한 테넌트 폭주가 전 테넌트를 멈춘다 |
| 주민등록번호 | 미저장, 유형 코드만 | 개인 대상 매출 테넌트가 발급 불능이 된다. BusinessType.Code 02 는 13자리를 실제로 요구한다. **암호화 저장 + 접근통제 + 파기 정책**이 맞다. 검증은 2020-10 이후 발급분에 체크섬이 무효이므로 **경고만** |
| 휴폐업 조회 | 현재 상태로 경고 | 폐업자 수취분도 **폐업일(end_dt) 이전 공급분은 정상 공제**된다. `b_stt_cd` 만 보지 말고 end_dt 와 공급시기를 비교. 조회 시각을 화면에 병기. 저장 차단은 기본값 금지 |
| 대표자성명 근거 | "필요적 기재사항" | 부가세법 제32조①은 공급받는자 측에 **등록번호만** 필요적이다. 상호·대표자성명·업태·종목은 임의적 기재사항(시행령 제67조②). 전자세금계산서 XML 이 1..1 로 요구하는 것은 **별개 층위**다 |

> ⚠ 마지막 항목을 KB 에 명시하지 않으면 "대표자명 결측 = 매입세액 불공제"라는 잘못된 검증이 코드에 박힌다.

## 5. 2차 — 심사가 갈린 지점 (사람이 결정)

| | 아키텍트 | 세무실무 |
|---|---|---|
| 2차 | 전자세금계산서 발급 (자격증명 3층 → 어댑터 → 샌드박스 1건 → 실패 경로) | **홈택스 매입·매출 자료 수집** → 부가세 신고 산출물 → 세무대리인 인계 포맷 |
| 논거 | 1차에서 만든 필드가 국세청 규격에 맞는지 증명하는 유일한 수단 | 부가세 신고서 (10)~(18)은 **받는 자료**라 ERP 가 생성하지 못한다. 발급만 만들면 매입란이 영구히 빈다 |

세무실무 측 근거: 국내 경쟁 제품(더존 Smart A)의 실제 판매 포인트가 "전자세금계산서·신용카드·현금영수증 자료수집 → 분개 → 전표입력"이다. 팝빌 기준 홈택스 수집은 **월 30,000원 정액**이며 테넌트가 홈택스 부서사용자 계정을 등록하는 방식이다.

한국 중소기업 회계의 실제 종점은 사내가 아니라 **세무대리인**이다. 세무사랑 3종(일반전표·신용카드 매입/매출·기타 매입/매출)과 더존 iplus 매입매출전표 엑셀 익스포트가 인계 포맷으로 거론됐다.

## 8. 알려진 한계

- **2차 분기(§5)가 미결이다.** 1차는 어느 쪽이든 동일하므로 착수를 막지 않지만, 필드 설계 세부가 달라진다.
- 부가세 **신고 단위는 회사가 아니라 사업장**이다. 종사업장번호를 Company 에만 두고 전표 전파를 미루는 것은 수용 가능하나, 주사업장 총괄납부·사업자단위과세 테넌트가 들어오면 축 설계를 다시 손대야 한다. 온보딩 심사에 "다사업장 여부"를 넣어 1차 대상에서 배제하는 운영 규칙이 필요하다.
- **간이과세자·면세사업자 분기**가 축 설계에 반영돼 있지 않다. 간이과세자는 서식이 다르고(별지 제44호) 신고 주기가 연 1회(익년 1/25)이며, 직전연도 공급대가 4,800만원 미만이면 세금계산서를 발급할 수 없다. 면세사업자는 부가세법이 아니라 소득세법·법인세법에 따라 계산서를 발급한다.
- 국세청 표준코드 **미검증 33건**([KB-KOR-002](./KB-KOR-002_korean_chart_of_accounts.md))은 세무 검토 대기 상태다. 1차와 병렬로 사람이 처리한다.
- 심사는 조사 결과를 근거로 한 판단이며 **고객 인터뷰·매출 데이터에 기반하지 않았다.**
