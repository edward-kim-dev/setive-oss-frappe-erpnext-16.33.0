# KB-KOR-006: 전자세금계산서 연계 아키텍처

> **상태**: 설계 확정 전. §9 의 서면 확인 2건이 뒤집히면 구조가 바뀐다. 코드 착수 전 반드시 §9 를 먼저 읽는다.

## 1. 요약

SETIVE 는 전자세금계산서를 **직접 발급하지 않는다.** 국세청에 등록된 시스템사업자(ASP)의 발급 시스템에 발행을 요청·중계한다. 1순위 벤더는 **팝빌(㈜링크허브, 국세청 시스템사업자 인증번호 제41000203호)** 이다.

```
  ERPNext Sales Invoice
        │ on_submit → enqueue
        ▼
  SETIVE 중앙 게이트웨이  ──[LinkID/SecretKey + CorpNum]──▶  팝빌  ──▶  국세청
        │                                                     │
        │◀──────────── 파트너 URL 웹훅 (전 테넌트 1개) ────────┘
        ▼
  테넌트 사이트 (발행 상태 · 승인번호 영속 보관)
```

**제품 서사를 이렇게 통일한다**: "SETIVE 가 전자세금계산서를 발급한다"가 아니라 **"SETIVE ERP 는 등록 시스템사업자의 발급 시스템에 발행을 요청·중계한다."** 자체 전자서명·자체 국세청 전송 엔진을 만드는 순간 시행령 제68조⑥ 등록 대상이 된다(§8).

---

## 2. 국세청 직접 연계는 불가능하다

부가가치세법 시행령 제68조⑤ 가 인정하는 발급 경로는 넷뿐이다.

| 호 | 경로 | SETIVE 적용 |
|---|---|---|
| 1호 | 표준인증 받은 **ERP 설비** | 등록·표준인증 필요 — §8 |
| 2호 | **발급대행사업자(ASP) 시스템** | ✅ 이 경로를 쓴다 |
| 3호 | 국세청 홈택스 | 수동 |
| 4호 | 현금영수증 발급장치 | 해당 없음 |

1호로 가려면 같은 조 제6항에 따라 국세청 등록이 필요하고, 시행규칙 제50조가 **위험관리계획서·전산조직운용명세서·대표자 보안서약서·표준인증·자본금 요건**을 요구한다. SETIVE 규모에서 현실적이지 않다.

- **e세로는 2015년 홈택스로 통합되어 폐지**됐다. 홈택스에는 개발자센터나 공개 OpenAPI 가 없다.
- 무료로 쓸 수 있는 국세청 API 는 공공데이터포털에 정확히 1건 — 「사업자등록정보 진위확인 및 상태조회」(`data.go.kr/data/15081808`, 자동승인, 1회 100건, 1일 100만건). 발급과는 무관하며 거래처 휴폐업·과세유형 판정용이다.

## 3. 벤더 비교

| | **팝빌**(링크허브) | 볼타(Bolta) | 바로빌(케이넷) |
|---|---|---|---|
| 프로토콜 | REST | REST/JSON, Basic | **SOAP/WSDL 전용** |
| 파이썬 SDK | ✅ `popbill` 1.64.2 (2026-06-08, MIT, 의존성 `linkhub` 1개) | ❌ (OpenAPI 3.1 공개) | ❌ (zeep 직접 구성) |
| 다중 테넌트 | 파트너키 1벌 + `CorpNum` | `POST /v1/issuers` | CERTKEY + 회원사 |
| 고객 계정 계층 | 연동회원(ID/PW) 필요 | **계정 없음** (필드 3개) | 회원사 필요 |
| 웹훅 | ✅ 파트너 URL (다중 회원사 통합) | ✅ | ❌ **폴링 필요** |
| 공개 단가 | 비공개(협의) | **정발행 90원** / 수정 90원 / 역발행 200원 | 비공개 |
| 부가 서비스 | 현금영수증·문자·알림톡·팩스·**홈택스 매입매출 수집**·계좌조회·휴폐업조회 | 세금계산서·현금영수증 | 다수 |
| 오류 처리 | `PopbillException`(음수 8자리) | HTTP + `cause.code` | **음수 5자리 반환값** — 모든 호출부에 부호 검사 + `GetErrString` 2차 호출 |

**팝빌 1순위 근거**: 유일한 공식 파이썬 SDK, 파트너 URL 웹훅(테넌트가 늘어도 콜백 엔드포인트 1개), 홈택스 수집이 같은 인증 체계 안에 있음.

**볼타 — PoC 1순위 / 운영 2순위** (2026-09-15 재평가): 연동회원 계정 계층이 없어 고객 단계가 1개 적고, **단가를 공개하는 유일한 곳**이라 협상 앵커로 쓸 수 있다. 결정적으로 **영업 접촉·심사·계약·공동인증서 없이 지금 당장 연동 검증이 가능하다**(§10). 볼타 문서가 **"대리 정발행"**(플랫폼이 공급자를 대신해 발행: 발급자 등록 → 인증서 등록 URL 발급 → 공급자가 직접 등록 → 대리 정발행 → 웹훅)을 **공식 사용 사례로 제시**하며, 이는 SETIVE 구조와 정확히 일치한다. 제약: 인증서 등록 URL 5분 만료, 등록내역 30초 조회 제한.

벤더 어댑터를 처음부터 추상화해 갈아탈 수 있게 둔다.

**토스(비바리퍼블리카) 계열 — 후보군에서 영구 제외** (2026-09-15 확인): 전자세금계산서 발급 API 가 **없다.** 토스페이먼츠 API 레퍼런스의 최상위 섹션은 결제 / 자동결제(빌링) / 거래 / 정산 / 현금영수증 / 프로모션 6개이고 "세금계산서"가 **섹션·엔드포인트·ENUM·용어집·FAQ 어디에도 등장하지 않는다.** 계열사 9곳 중 B2B 세무 사업자가 없고, 유일한 세무 계열사 토스인컴은 B2C 환급 전용으로 스스로 "세금 상담 및 세무 대리 업무를 제공하지 않아요"라고 명시한다. 삼쩜삼은 자비스앤빌런즈㈜ 운영으로 **토스 계열이 아니다.** → 다음 에이전트가 같은 조사를 반복하지 않도록 기록한다. 토스의 현금영수증 API 는 별개 논점이며 §12 에 둔다.

**스마트빌 제외**: 비즈니스온커뮤니케이션 제품(더존 아님, 더존은 Bill36524). API Key 가 각 기업 관리자 수동 승인에 묶이고 SDK 가 Java/.NET 뿐.

> 과제에서 지목된 "이지빌"·"아이티엠(넥스트빌)"은 전자세금계산서 API 사업자로 확인되지 않았다. ITM 계열로는 GS ITM 의 U.STRA BILL 이 있으나 공개 개발자 문서가 없다.

## 4. 팝빌 파트너 단일키 모델

### 4.1 회원 3계층

```
  파트너 (SETIVE)              LinkID + SecretKey        ← 계약 필수
    └ 연동회원 (고객사)        CorpNum (사업자등록번호)   ← 중복 등록 불가
        └ 담당자               UserID
```

**"팝빌에 SETIVE 만 가입한다"는 성립하지 않는다.** 공식 FAQ 원문:

> "프로그램을 연동하여 고객사에 팝빌 API를 제공할 수 있나요? / 네, 가능합니다. **단, 고객사가 팝빌에 파트너의 연동회원으로 가입해야 합니다.**"

다만 가입을 `joinMember()` 로 SETIVE 가 코드로 대행하므로 **고객 체감으로는 "가입 안 함"** 이다. SDK 가 `LinkID` 를 자동 주입한다.

```python
# popbill/base.py
def joinMember(self, JoinInfo):
    JoinInfo.LinkID = self.__linkID          # 파트너 키 자동 주입
    return self._httppost("/Join", self._stringtify(JoinInfo))
```

필수 필드: `ID` `Password` `CorpNum` `CEOName` `CorpName` `Addr` `BizType` `BizClass` `ContactName` `ContactEmail` `ContactTEL`.
→ **업태(BizType)·종목(BizClass)·대표자명은 ERPNext `Company` 에 없다.** [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) M2 의 신원 필드가 이 연계의 선행 조건인 이유다.

### 4.2 과금 — 파트너 결제

출처: `developers.popbill.com/guide/taxinvoice/getting-started/billing` (현금영수증·문자 가이드에 동일 게재)

| 구분 | 파트너 결제 | 연동회원 결제 |
|---|---|---|
| 결제 주체 | **파트너** | 연동회원 |
| 과금 기준 | 하위 전 연동회원 **합산** | 연동회원별 |
| 제휴 수수료(리셀링) | **해당 없음 (원가 제공)** | 지원 (원가+마진) |
| 결제 조건 | 선불 또는 **후불(조건부)** | 선불만 |

> "파트너 과금 방식의 경우 **연동회원에게는 API 상품 이용 요금 및 잔여포인트가 표시되지 않으며**, 파트너 관리자 사이트에서 연동회원별 사용내역을 확인할 수 있습니다."

**마진은 팝빌 정산이 아니라 SETIVE 요금제 안에 녹인다.** 팝빌에서 원가로 사고 SETIVE 가 자체 요금으로 청구하는 구조다. 팝빌이 정산으로 마진을 지급하는 리셀링 제도는 연동회원 결제 전용이며, 그쪽을 택하면 고객이 팝빌에 직접 선불 충전해야 해 화이트라벨이 무너진다.

테넌트별 사용량 집계는 `GetUseHistory(CorpNum, SDate, EDate, PerPage≤1000)`, 파트너 잔액은 `GetPartnerBalance(CorpNum)` 로 조회한다.

### 4.3 영업 하드 제약 — 사업자번호 중복 등록 불가

> "연동회원은 … **사업자등록번호 기준으로 관리되어 중복 등록은 불가**합니다."

이미 더존·이카운트 등 타 공급사 하위 연동회원이거나 팝빌 일반회원인 사업자는 **SETIVE 가 대리가입할 수 없다.** 타 파트너 소속 회원의 이관 공식 경로는 문서에 없다.

→ **계약서 서명 전에 `checkIsMember(CorpNum)` 사전 진단을 영업 프로세스에 넣는다.** 테스트 계정을 받는 즉시 구현 가능한 가장 작은 첫 코드다.

## 5. 인증서 — 유일하게 제거 불가능한 고객 부담

전자서명이 법적 요건이라 **팝빌·바로빌·볼타 셋 다 공급자 본인 명의 인증서를 요구한다.** 위수탁도 우회로가 아니다 — 부가세법 시행령 제69조의 위탁판매·대리판매 관계에서만 성립하고, 이때도 **수탁자 인증서**로 서명하며 수탁자 사업자번호가 계산서에 기재된다.

### 5.1 등록은 ERP 안에서 끝낼 수 있다

| 경로 | 고객 경험 | 비고 |
|---|---|---|
| `RegistTaxCertPFX(pfx, password)` | ERP 화면에서 파일+비번 입력. **팝빌 도메인을 보지 않음** | **Python SDK 미구현 — REST 직접 호출** |
| `RegistTaxCert(certPublicKey, certPrivateKey, certCipher)` | NPKI 폴더 보유 고객용. pfx 변환 불요 | 〃 |
| `GetTaxCertURL(CorpNum, UserID)` | 팝빌 팝업 | **폴백 전용.** URL 30초 만료 → 버튼 클릭 시점에 호출 |

> ⚠ 팝업 경로는 로컬 설치형 **"인증서 툴킷"** 에 의존한다. 팝빌 공식 블로그(2025-12-11)가 Chrome/Edge 141+ 의 Local Network Access 정책 때문에 툴킷 설치가 막히는 문제와 `chrome://flags` 수준 해결법을 안내 중이다. 비개발자 고객에게 이 화면이 뜨면 온보딩이 무너진다.

FLE(필드 레벨 암호화) 통신구간 키가 없으면 `RegistTaxCertPFX` 를 쓸 수 없다. **이 키 발급이 온보딩 UX 전체의 선행 병목**이며 파트너센터에 별도 신청한다.

### 5.2 보안 — 협상 불가 항목

`RegistTaxCertPFX` 를 쓰면 고객 인증서 파일과 비밀번호가 SETIVE 를 경유한다. **전 테넌트의 전자서명 수단을 한곳에 모은 표적**이 된다.

- 브라우저에서 팝빌 FLE 공개키로 암호화한 뒤 전송해 **SETIVE 서버·로그·DB 에 평문이 존재하지 않게** 한다.
- 불가능한 키 사양이면 서버 메모리 내 처리 후 즉시 파기 + 저장 금지 + 접근 감사를 못 박고, 고객 약관에 **전자서명 수단 위탁의 범위와 책임**을 명시한다.
- 팝빌조차 "필요 시점에 한시적 사용 후 자동 파기"를 명시한다.

### 5.3 인증서 조달 (SETIVE 대행 불가, 비용 대납은 가능)

| 종류 | 비용 | 비고 |
|---|---|---|
| 전자세금계산서용 (은행 발급) | 4,400원/년 | **기존 사업자 다수가 이미 보유 → 추가 비용 0원** |
| 팝빌 표준 3년형 (TradeSign) | 40,000원 | 비대면 당일발급. **3년형 권장 — 재개입 주기 3배** |
| 팝빌 표준 1년형 | 20,000원 | 대면 전용, 2~5일 |
| 전자거래 범용 | 110,000원/년 | |

**사용 불가**: 금융거래용·인터넷뱅킹 인증서, 타기관 특수목적용.

미보유 고객에게 ERP 안에 체크리스트 4줄을 렌더하면 발급 실패 재시도가 줄어든다 — (a) 3년형 권장 (b) 평일 16시 이전 신청해야 당일발급 (c) 공동대표 법인은 비대면 불가 (d) 정부24에서 사업자등록증명원 '문서 열람용번호'를 제출처 ㈜한국무역정보통신 지정해 미리 발급.

### 5.4 금융인증서·간편인증은 아직 안 된다

2024-06-25 출시 전자세금용 금융인증서(연 4,400원)와 2026-04-22 도입 국세청 사업자용 간편인증은 **홈택스·손택스 전용**이며 ASP 확대는 "유관기관 협의 계획" 단계다. 팝빌 현행 허용 목록에 없다.

→ **된다고 가정한 설계를 하지 않는다.** 다만 지원되는 순간 온보딩 인증서 조달 단계가 통째로 사라지므로 **분기 단위로 재확인**한다.

### 5.5 만료 관리 (자동화 가능)

| API | 용도 |
|---|---|
| `GetCertificateExpireDate(CorpNum)` | 만료일 (`yyyyMMddHHmmss`) — 주 1회 폴링, D-60/30/14/7 알림 |
| `CheckCertValidation(CorpNum)` | 유효성 — 일 1회, 폐기·무효 감지 |
| `GetTaxCertInfo(CorpNum)` | `issuerName` · `subjectDN` — 등록 직후 사업자번호 일치 검증 |
| `UpdateEmailConfig(ETC_CERT_EXPIRATION, true)` | 팝빌이 고객에게 만료예정 메일 직접 발송 (SETIVE 알림과 이중화) |

> 인증서 만료·무효 상태에서 **Sales Invoice 제출을 막지 않는다.** 전표는 제출시키고 발행만 '대기' 큐에 넣는다. 만료가 월말·분기말에 몰리면 마감 업무 전체가 멈춘다.

## 7. 포크 수정 없이 구현 가능하다 (코드 실측)

| 필요 확장점 | 도달 경로 | 실측 근거 |
|---|---|---|
| 제출 시 발행 큐잉 | `doc_events["Sales Invoice"]["on_submit"]` | `append_hook` 이 리스트를 **extend** 하므로 코어 italy 훅과 **공존**(경합 아님) |
| 발행 실패 시 제출 차단 | `on_submit` 에서 `frappe.throw` | `frappe/app.py` 의 except 절이 `db.rollback(chain=True)` → docstatus=1 까지 되돌아감 |
| 취소 차단 | `regional_overrides` + `doc_events["before_cancel"]` **이중화** | 아래 ⚠ 참조 |
| 웹훅 수신 | 앱의 `@frappe.whitelist(allow_guest=True)` | |
| 상태 폴링 | `scheduler_events` | ⚠ 신규 사이트는 `enable_scheduler=0` 이고 이 스택 어디에도 `enable-scheduler` 가 없다 |
| 신규 DocType·Print Format | 앱 모듈 폴더 + `bench migrate` | ⚠ 컨테이너 기동 스크립트에 `bench migrate` 가 없어 새 DocType JSON 이 디스크에만 남는다 |

### 7.1 `regional_overrides` 는 한국에서 동작한다 — 이전 이해 정정

[CLAUDE.md](../../CLAUDE.md) 와 [KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §2.5 는 `frappe.scrub("Korea, Republic of")` 의 쉼표 때문에 한국 regional 이 무증상 실패한다고 기술한다. **이는 `erpnext/regional/<scrub(country)>` 패키지 import 경로에만 해당한다.**

`regional_overrides` 훅은 국가명 **문자열 키**로 조회하므로 `"Korea, Republic of"` 가 그대로 먹는다. 코어에 `@erpnext.allow_regional` 로 표시된 `validate_einvoice_fields(doc)` 가 `AccountsController.validate` 와 `before_cancel` 두 곳에서 호출된다.

> **전자를 후자까지 확장 적용하면 쓸 수 있는 확장점을 스스로 버린다.** `erpnext/regional/korea/` 디렉터리를 만들지 않는다는 금지는 그대로 유효하다.

⚠ **단, `before_cancel` 경로는 신뢰할 수 없다.** `accounts_controller.py` 의 `validate` 는 `with temporary_flag("company", self.company)` 로 감싸여 있으나 `before_cancel` 에는 **없다.** `get_region()` 이 `frappe.local.flags.company` → `frappe.flags.country` → System Settings.country 순으로 떨어지므로, 취소 시점에는 Company 국가가 아니라 **System Settings 국가로 판정될 수 있다.** 현재 앱이 `system_defaults` 로 System Settings 를 한국으로 맞추고 있어 우연히 동작할 뿐이다. → 취소 차단은 `doc_events` 로 이중화하고, 스파이크에서 실제 취소 경로의 `get_region()` 반환값을 로그로 확인한다.

### 7.2 트랜잭션 함정 — 세 컨텍스트를 구분한다

| 컨텍스트 | `frappe.db.commit()` | 의미 |
|---|---|---|
| (a) doc_event 훅 실행 구간 | **무시됨** (`_disable_transaction_control` 이 올라감, 경고만) | "국세청엔 발급됐는데 DB 엔 흔적 없음"이 구조적으로 가능 |
| (b) `after_commit` 콜백 | 정상 | |
| (c) RQ 워커 잡 | 정상 (별도 요청 컨텍스트) | |

`enqueue_after_commit=True` 가 막아주는 것은 **"제출 롤백 → 발급 없음"** 이다. 막지 못하는 것은 **"발급 성공 → 이후 전표 취소"** 라는 역방향이며, 이쪽 방어는 일일 대사뿐이다. → **대사를 선택 기능이 아니라 필수로 둔다.**

### 7.3 멱등성

ERPNext 의 재시도·중복 제출로 같은 Sales Invoice 가 두 번 발행되면 **수정발행으로만 되돌릴 수 있다.** 어댑터 인터페이스에 **"테넌트 스코프 관리번호"를 1급 인자**로 넣는다 — 나중에 끼워 넣을 수 없다.

- 팝빌: 문서관리번호 `MgtKey` + `checkMgtKeyInUse`
- 볼타: `Bolta-Client-Reference-Id` 헤더 (409 `IDEMPOTENCY_CONFLICT`)

> 발행 이력 DocType 의 `autoname` 을 **승인번호로 하지 않는다.** 스키마 오류 시 국세청이 `9999999999999999xsderror` 를 반환해 충돌한다. `mgt_key` 기반 autoname + 승인번호 unique index 로 만든다.

### 7.4 워커 재설치 누락 시 증상이 다르다

[CLAUDE.md](../../CLAUDE.md) 는 앱 pip 재설치 누락 시 "사이트 전체 HTTP 500"을 기술한다. 그러나 `popbill` 이 backend 에만 설치되고 워커 3종(`queue-short`·`queue-long`·`scheduler`)에 빠지면 **웹은 정상인데 발급 잡만 조용히 실패**한다. 증상이 달라 진단이 늦으므로 검증에 "워커에서 import 가능한가"를 별도 항목으로 넣는다.

### 8.1 책임 전가 구조 (주의)

팝빌 약관 제24조②는 배상 총액을 "직전 12개월간 **회원이** 해당 서비스 이용의 대가로 **회사에 실제 지급한 금액**"으로 한정한다. 파트너 결제에서는 **연동회원이 팝빌에 지급한 금액이 0원**이다. 팝빌 장애로 고객에게 가산세가 발생하면 회수 경로가 SETIVE 로 집중된다.

→ SETIVE 고객 약관에 (가) 발급의무·가산세는 공급자인 고객에게 귀속 (나) SETIVE 는 중계할 뿐 국세청 승인·전송 결과를 보증하지 않음 (다) 마감 임박 발행 시 고객의 결과 확인 의무 (라) 배상 한도와 간접손해 배제를 넣되, **약관규제법상 고의·중과실 면책은 무효이므로 "고의 또는 중대한 과실의 경우에는 그러하지 아니하다" 단서가 필수**다.

## 10. 검증 — 계약 전에 할 수 있는 것과 없는 것

> ### ⚠ 이전 서술 정정 (2026-09-15 실측)
>
> 이 문서의 이전 판은 **"테스트는 전 벤더 무료다. 계약 전 0원으로 PoC 가 가능하다 / 팝빌: `IsTest=True` + 공개 테스트키 `LinkID="TESTER"`"** 라고 기술했다. **팝빌에 대해서는 틀렸다.**
>
> 공개 TESTER 키는 `auth.linkhub.co.kr` 에서 **토큰 발급이 차단된다** — HTTP 400 / `-99010013 "인증정보(LinkID, SecretKey)를 변경하여 주시기 바랍니다"`.
>
> 자리표시자가 아니라 **실존하지만 의도적으로 막아둔 공유 데모 키**다. 대조 실험으로 서명 구현 오류 가능성을 배제했다:
>
> | 조건 | 응답 |
> |---|---|
> | TESTER + 정상 SecretKey | HTTP 400 / `-99010013` (발급 거부) |
> | SecretKey 1바이트 훼손 | HTTP 401 / `-99010007` (서명 불일치) |
> | 존재하지 않는 LinkID | `-99004021` (링크아이디 미존재) |
>
> 세 코드가 갈린다는 것은 TESTER 가 실존 LinkID 이고 **서명 검증까지 통과했으나 토큰 발급 단계에서 정책적으로 거부**된다는 뜻이다. `POPBILL_TEST`/`POPBILL` 양쪽, scope 조합, forwardIP 유무 6변형 모두 동일했다.
>
> → **`checkIsMember`·`joinMember` 를 포함한 모든 팝빌 API 를 계약 전에 호출할 수 없다.**
>
> 함께 정정: "테스트 환경은 팝빌 제공 테스트 인증서로 진행 가능"은 맞지만, 그 **인증서 신청 폼(`/customer-center/requestcert`)이 LinkID 와 사업자번호를 필수로 요구**한다는 조건을 빠뜨렸다. 계약 전에는 팝빌 테스트 발행 자체가 불가능하다.
>
> ⚠ 구현 시 주의: 팝빌 공식 예제의 SecretKey 마지막 문자는 **`…q3I=`(대문자 아이)** 다. `…q3T=` 로 잘못 옮기면 차단(`-99010013`)이 아니라 **서명 실패(`-99010007`)** 가 나와 "내 서명 구현이 틀렸나"로 오진하게 된다.

| 벤더 | 계약 전 PoC | 근거 |
|---|---|---|
| **팝빌** | **불가** | 위 실측. 연동신청(사업자번호·업태·종목 필수)을 통과해야 API Key 가 나온다 |
| **볼타** | **가능** | 구글/이메일 가입 → 워크스페이스 → 개발자센터에서 `test_` 키 **버튼 한 번으로 자체 발급**(승인 절차 없음) → 발급자 등록(3필드) → **테스트 인증서로 발행**까지. 공식 문서: "별도 계약 없이 개발자센터에서 포인트를 충전한 후 바로 이용", "테스트 환경에서는 테스트 인증서를 사용할 수 있어 실제 공동인증서가 없어도 연동 테스트가 가능" |
| 바로빌 | 미검증 | `testws.baroservice.com` + 테스트용 연동인증키 |

> 볼타도 **무장벽은 아니다** — 워크스페이스 생성에 사업자등록증 기준 회사 정보가 필요하고, 발급자 등록 API 의 사업자등록번호는 **체크섬 검증**을 받는다. 정확히는 "**사람 게이트(영업·심사·계약)가 없을 뿐**"이다.

> 팝빌은 테스트(`test.popbill.com` / `POPBILL_TEST`)와 운영(`popbill.com` / `POPBILL`)이 **완전 분리**되어 데이터·인증서·연동회원이 이관되지 않는다. 볼타는 `xapi.bolta.io` 단일 도메인에 **키 접두사(`test_`/`live_`)로만** 환경이 갈린다 → [KB-OPS-002](./KB-OPS-002_tenant_integration_credentials.md) §5.

## 11. 알려진 한계

### 11.1 사업자등록이 크리티컬 패스 위에 있다 (2026-09-15 추가)

연동신청 폼이 사업자번호뿐 아니라 **업태·종목**까지 필수로 요구하고, 이 둘은 사업자등록증 기재사항이라 만들어낼 방법이 없다. **사업자등록 없이는 팝빌 API Key 를 받을 수 없고, TESTER 공개키 우회도 막혀 있다**(§10).

**다만 서류 부담은 생각보다 뒤에 있다.**

```
   사업자등록  →  연동신청(첨부서류 0건)  →  개발·테스트  →  운영전환(사업자등록증+계약)  →  실발행
        ▲                                                          ▲
   여기만 넘으면                                          서류·계약은 여기서
   개발은 즉시 착수                                        (전자계약 1일)
```

개인사업자도 **대표자 휴대폰 인증만으로 전자계약**이 가능하므로(법인은 법인명의 범용 공동인증서) 법인 설립을 기다릴 필요가 없다. 팝빌은 운영전환 단계에서 법인/개인사업자를 나누어 지원한다.

> ⚠ **이 제약이 1차 작업을 막지 않는다.** [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) 의 M1~M4(식별번호 체크섬·신원 필드·설정 계층·국세청 무료 조회)는 외부 계약이 한 건도 필요 없다. 팝빌이 막혔다는 이유로 1차까지 멈추지 않는다.

### 11.2 그 밖

- §9 의 **1·2번이 미확인**이다. 이 문서의 과금·온보딩 설계는 그 답에 의존한다.
- 팝빌 **파트너 단가가 비공개**다. 원가 확정 전에 SETIVE 요금표를 고정하지 않는다.
- 파트너 계약 체결·운영전환 **소요 기간**이 공개 문서에 없다("유선 협의"로만 표기).
- **역발행**(공급받는자 작성 → 공급자 승인) 지원 여부 미결. 단가가 정발행의 2배 이상(볼타 200원 vs 90원)이고 승인 UX 가 붙는다.
- 국세청 전송 반려(팝빌 상태코드 305) 상태를 Sales Invoice 상태와 어떻게 대응시킬지는 **벤더와 무관한 SETIVE 설계 결정**이며 미정이다.
- 볼타의 **파트너/리셀러 제도·후불·issuer 수 상한**이 공개 문서에 없어 대안으로서 완전히 검증되지 않았다.
- 이 문서의 팝빌 서술은 **공개 문서 기준**이다. 계약서 원문을 보지 못했다.
- **API Key 수령까지의 공식 SLA 가 어디에도 없다.** 운영전환만 "전자계약 1일 / 등기계약 최소 5일"이 명시돼 있다.
- 개발자센터 약관 제4조 1)은 회원을 "연동신청한 **사업자 또는 개인**"으로 쓰지만, 팝빌 **본 서비스** 약관 제4조 5)는 회원을 명시적으로 "**사업자**"로 정의한다. 연동신청이 운영 계정을 자동 생성하는 구조라 실무상 비사업자 등록은 성립하기 어려워 보이나 **실제 사례는 확인하지 못했다.**

## 12. 벤더별 테넌트 온보딩 비용 차이

| | 팝빌 | 볼타 |
|---|---|---|
| 테넌트 등록 | **계정 생성** — `checkID` 중복확인 + ID/PW + 담당자 11필드 | **계정 개념 없음** — `identificationNumber`·`organizationName`·`representativeName` 3필드 |
| 파이프라인 부담 | ID 중복 회피 규칙, 비밀번호 보관 주체 결정 필요 | 없음 |
| **인증서 등록** | **고객이 브라우저에서 직접** — 법적 요건, 우회 불가 | **동일** |

→ 어댑터 인터페이스에 **"인증서 등록 상태 머신"**('URL 발급 → 고객 이동 → 복귀 → 등록결과 조회')을 공통 계약으로 박아둔다. 이 부분만은 어느 벤더로 가도 같다.

### 12.1 토스 현금영수증 — 조건부 후보 (전자세금계산서와 무관)

토스페이먼츠는 `POST /v1/cash-receipts` / cancel / GET 를 제공하고, **"현금영수증 가맹점이라면 토스페이먼츠로 결제하지 않은 건도 발급 및 취소 요청을 할 수 있다"** — 결제와 분리된 단독 발급이 된다. **무료**이며 PG 가맹점이 아니어도 회원가입만으로 쓸 수 있다고 공식 사이트가 명시한다(팝빌은 현금영수증도 건당 과금). `type` 이 `지출증빙/PROOF`(B2B) · `소득공제/DEDUCTION`(B2C)로 갈린다.

> ⚠ **확인 전에는 로드맵에 올리지 않는다.** 두 가지가 미확인이고 둘 다 로그인 벽이라 문서로 확인할 수 없다.
> 1. 무료 회원가입만으로 **API 시크릿 키까지 나오는가** — API 키 문서는 "연동 키는 전자결제 신청 이후에만 확인할 수 있어요"라고 한다.
> 2. **SaaS 인 SETIVE 가 테넌트를 대신해 발급하는 멀티테넌트 구조가 성립하는가** — 국세청에 기록되는 가맹점 명의가 누구인지, 팝빌의 파트너/연동회원에 해당하는 개념이 있는지가 문서에 없다. **이게 안 되면 자리가 사라진다.**
