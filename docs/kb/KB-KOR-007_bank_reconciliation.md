# KB-KOR-007: 은행 입금 대사 아키텍처

> **상태**: 설계만 있고 구현 0. 착수는 [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) 로드맵상 전자세금계산서 이후다. 이 문서는 **벤더 협상을 전자세금계산서와 한 번에 묶기 위해** 미리 작성했다.

## 1. 요약

매출채권 회수를 자동 대사하려면 은행 입금 내역을 가져와야 한다. ERPNext 에 `Bank Reconciliation` 이 있으나 한국 은행 연동이 없다.

**성패는 단 하나로 갈린다 — 입금자명(적요)이 API 로 오는가.**

| 경로 | 입금자명 | 판정 |
|---|---|---|
| **팝빌 계좌조회 (easyFinBank)** | `remark1~4` 중 **은행마다 다른 위치** | **1순위 (단기)** |
| **오픈뱅킹 법인계좌 조회** (2025-01-02 시행) | **'통장인자내용(의뢰인·수취인·적요)' 표준 항목** | **최종 목적지 (중기)** |
| 토스페이먼츠 가상계좌 | 웹훅 본문에 **없음** | **부적합** |
| 펌뱅킹 직접 계약 | 은행별 상이 | 규모 전 부적합 |

→ **`BankStatementProvider` 인터페이스를 먼저 긋고 팝빌을 첫 구현체로 만든다.**

---

## 2. 팝빌 계좌조회를 1순위로 두는 이유

| 근거 | 내용 |
|---|---|
| 벤더 단일화 | 전자세금계산서와 **같은 LinkID/SecretKey·같은 포인트 체계** (scope 180 계좌조회 / 182 예금주 성명조회 / 183 실명조회) |
| 진입 비용 | 기본료·도입비 **0원**, 연동 테스트 **1개월 무상**. 테스트 환경이 더미가 아니라 실제 은행 거래정보를 수집 |
| 규제 방어선 | 은행 '빠른조회 서비스' 기반이라 **이체가 구조적으로 불가능**하다. SaaS 가 고객 자금을 움직일 수 없다는 점이 보안·규제상 방어선이 된다 |
| 구조 재사용 | 파트너–연동회원 2계층이 그대로 → [KB-KOR-006](./KB-KOR-006_etax_invoice_integration.md) §4 |

공동인증서가 **필요 없다**(계좌번호·계좌비밀번호 등록 + 은행 빠른조회 신청). 전자세금계산서와 달리 이 축은 인증서 부담이 없다.

> ⚠ **스크래핑 기반이다.** 이 사실을 여기 명시해 두는 이유는, 정책이 바뀌었을 때 다음 사람이 "왜 이 경로를 골랐는지"와 "무엇을 지켜보고 있어야 하는지"를 알 수 있게 하기 위함이다. §6 참조.

## 3. 최대 난점 — 입금자명이 어디에 오는지 은행마다 다르다

팝빌 `EasyFinBankSearchDetail` 에는 **입금자명 전용 필드가 없다.**

| 필드 | 내용 |
|---|---|
| `tid` | 거래내역 아이디 — **멱등 키** |
| `trdt` | 거래일시 |
| `accIn` / `accOut` | 입금액 / 출금액 |
| `balance` | 잔액 |
| **`remark1` ~ `remark4`** | 적요 4칸. **어느 칸이 의뢰인인지가 은행마다 다르다** |

실례: 기업은행 `remark1` = 받는분 계좌번호, 국민은행 `remark1` = 내통장 표시내용, 예시상 `remark3` = "(주)팝빌상사".

### 3.1 설계 결론

```
   Bank Transaction (ERPNext)
     ├ remark1 · remark2 · remark3 · remark4   ← 원본 그대로 4필드 보존
     └ (파생) depositor_name                    ← 아래 규칙으로 추출

   Bank Remark Rule (신규 DocType)
     └ bank_code → 의뢰인이 담긴 remark 번호
```

> **정규화 후 원본을 버리면 은행이 하나 늘 때마다 복구 불가다.** 원본 4필드는 반드시 남긴다.

### 3.2 정확도 보강 — 예금주조회 선행

한국 실무에서 입금자명은 법인명이 아니라 **담당자 개인명**으로 찍히는 일이 흔하다. 팝빌 예금주조회(성명 50원/건)를 `Customer`/`Supplier` 은행계좌 마스터에 붙여 거래처 출금계좌의 예금주명을 **미리 확보**하면 이 문제를 대사 이전 단계에서 흡수할 수 있다.

## 4. 팝빌을 원장으로 삼을 수 없다

| 제약 | 값 |
|---|---|
| 조회 가능 기간 | 현재일 기준 **과거 3개월** |
| 1회 조회 범위 | 최대 **1개월** |
| 지원 범위 | 19개 은행, **원화 일반계좌만** |

→ **ERPNext 가 영속 원장**이어야 한다. `tid` 를 멱등 키로 잡아 중복 적재를 막고, 수집 스케줄러 주기는 **계약한 조회주기(3/5/10/20/30분)와 일치**시킨다. 주기 전에 호출하면 직전 성공 시점까지의 같은 데이터만 돌아온다.

## 5. 토스는 이 자리에 들어오지 않는다

토스페이먼츠 가상계좌는 **'결제 수단 추가'이지 '입금 대사'의 답이 아니다.**

1. 자금이 **PG 를 경유**하고 정산이 평균 T+5일. 건당 400원 + 가입비 220,000원 + 연관리비 110,000원.
2. `DEPOSIT_CALLBACK` 웹훅 본문에 **입금자명이 없다** — `createdAt`/`secret`/`status`/`transactionKey`/`orderId` 5개뿐. 결제 조회를 한 번 더 해야 `virtualAccount.depositorName` 이 나오는 **2-hop** 구조다.
3. 공식 FAQ 가 "결제 금액만 정확히 입금되면 구매자와 입금명이 달라도 정상 처리"라고 적었듯 **애초에 입금자명이 대사 키가 아니다.**
4. 결정적으로 **세금계산서 발행 후 기존 법인 주거래계좌로 들어오는 외상매출 회수는 이 경로로 전혀 잡히지 않는다.**

`/v1/transactions`·`/v1/settlements` 도 PG 거래·정산 조회이지 은행 계좌 입출금이 아니며, `vat`·`supplyAmount` 는 **결제 수수료**의 부가세·공급가액이지 매출 세금계산서가 아니다. 토스뱅크의 기업 대상 공개 오픈 API 는 사이트맵·개발자 포털 어디에도 확인되지 않는다.

> **다만 SETIVE 자신의 SaaS 구독료 수납**에는 고정 가상계좌가 잘 맞는다. `accountKey` 를 테넌트 ID 로 잡으면 입금자명 파싱 없이 테넌트를 특정할 수 있다. **이건 제품 기능이 아니라 회사 운영 인프라**이고, 추가 심사·계약이 붙으므로 테넌트가 쌓인 뒤 일이다. 두 기능을 같은 로드맵 항목으로 묶지 않는다.

## 6. 중기 전환 대상 — 오픈뱅킹 법인계좌 조회서비스

2025-01-02 시행. 거래내역 대상정보에 **'통장인자내용(의뢰인, 수취인, 적요)'이 표준 항목으로 분리**되어 있어 데이터 품질이 압도적이고, 금융위 보도자료가 기대효과에 **ERP 를 명시**했다.

**지금 도입하지 않는 이유**: 공식 문서상 "서비스 은행 16개의 **기업뱅킹 채널**"을 통해 제공되는 구조여서 **비은행 SaaS 가 직접 중계할 수 있는지가 미확인**이고, 이용기관 등록 요건(자본금·보증보험·보안점검·수수료)도 확인하지 못했다. 사업자등록조차 확정되지 않은 단계에서 이쪽을 추진하는 것은 순서가 틀렸다.

**지금 할 일은 도입이 아니라 추상화 경계를 긋는 것**이다 — `korea/common/` 에 `BankStatementProvider` 인터페이스를 두고 팝빌을 첫 구현체로 만든다.

### 6.1 감시해야 할 규제 신호

- **2026-08-20 시행 개인정보보호법 시행령**의 '본인전송요구 대리인' 제도
- 대법원 스크래핑 차단(한시 유예 ~8.31) — **단, 확인된 사례는 공공 문서 발급이지 은행 계좌조회가 아니다.** 확대 적용을 단정하지 않는다.

방향은 "스크래핑 → 표준 전송요구 API" 전환 압력이다. 팝빌 경로가 은행이 공식 제공하는 **조회 전용 채널**이라는 점이 현재의 방어선이다.

## 7. 경쟁재와 가격 하한선

웹케시 **인하우스뱅크**(펌뱅킹 기반)가 "은행 입금내역을 ERP 로 전송해 수취 확인 자동화"를 이미 파는 제품이다. 중견기업은 이미 쓰고 있다.

→ SETIVE 의 표적은 **그걸 살 수 없는 규모**이고, **계좌당 월 원가(팝빌 협의 단가)가 곧 가격 하한선**이다.

> ⚠ 팝빌 공개 요금표의 계좌조회 **5,000원/월이 계좌당인지 회원당인지 명시가 없다**(10계좌 초과 할인 안내가 있어 계좌 기반으로 보임). 파트너 결제 원가와 조회주기별 단가표는 비공개다. → [KB-KOR-006](./KB-KOR-006_etax_invoice_integration.md) §9.2 질의 11번에 묶어 **전자세금계산서와 한 번에 협의**한다. 따로 물으면 협상력이 없다.

## 8. 검증 (구현 시)

```bash
SITE=localhost
COMPOSE=docker/development/docker-compose.yml
X="docker compose -f $COMPOSE exec -T backend bench --site $SITE"

# 1. 멱등 키 — 같은 기간을 두 번 수집해도 Bank Transaction 이 늘지 않아야 한다
$X execute setive_erpnext_kr.korea.common.bank_statement.collect \
  --kwargs '{"company":"<회사>","from_date":"2026-09-01","to_date":"2026-09-15"}'

# 2. 원본 보존 — remark1~4 가 비어 있지 않은지
$X execute frappe.client.get_list \
  --kwargs '{"doctype":"Bank Transaction","fields":["name","remark1","remark2","remark3","remark4"],"limit_page_length":5}'

# 3. 조회 기간 제한 — 3개월 초과 요청 시 한국어 예외가 나야 한다
```

## 9. 알려진 한계

- **구현 0.** 이 문서는 설계와 벤더 협상 준비다.
- 팝빌 계좌조회 **파트너 단가와 과금 단위가 미확인**이다(§7). 제품 가격을 정할 수 없다.
- **은행별 `remark` 매핑표가 없다.** 19개 은행 각각에 대해 실제 데이터로 확인해야 하며, 문서만으로는 만들 수 없다.
- 오픈뱅킹 법인계좌 조회의 **비은행 이용기관 직접 참여 가능 여부**가 미확인이다(§6).
- 외화계좌·증권계좌·법인카드 대사는 범위 밖이다.
- 이 조사는 WebSearch 예산 소진으로 일부 공식 사이트 직접 fetch 만으로 수행됐다. 영업 채널 전용 비공개 상품의 부재까지 증명하지는 못한다.
