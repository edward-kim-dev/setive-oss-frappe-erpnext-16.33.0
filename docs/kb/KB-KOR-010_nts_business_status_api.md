# KB-KOR-010: 국세청 사업자등록 진위확인·상태조회 API

> **상태**: 스펙 확보 + 실호출 검증 + **순수 파서 구현·검증 완료**(`korea/common/nts_bizinfo.py`).
> frappe 쪽 기록(로그 append·캐시 갱신)과 리포트 컬럼은 미착수 — 사이트가 필요하다. 파서·어댑터는 [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) §4 의 **M4** 소관이다.
> 이 문서는 그 착수 전에 확정해야 할 사실만 담는다.
> ⚠ **이 문서는 기존 KB 4종의 서술을 정정한다** — §8 을 먼저 읽는다.

---

## 1. 요약

트랙 1 에서 **실물 외부 호출이 가능한 유일한 API** 다. 무료·자동승인이고 사업자등록 없이 개인회원으로 키를 받을 수 있다(2026-09-17 실제 발급 확인).

```
POST https://api.odcloud.kr/api/nts-businessman/v1/validate   진위확인
POST https://api.odcloud.kr/api/nts-businessman/v1/status     상태조회
     ?serviceKey=<키>&returnType=JSON
```

| 축 | 결론 | 절 |
|---|---|---|
| 엔드포인트 | `POST` 2개. **GET 미지원** | §2 |
| 인증 | `serviceKey` **쿼리스트링**. 바디가 아니다 | §2·§6 |
| 진위확인 필수 | `b_no` · `start_dt`(YYYYMMDD) · `p_nm` **3개** | §3 |
| 상태 응답 | `BusinessStatus` **11필드**. 두 엔드포인트가 **공유**한다 | §4 |
| 과세유형 | **7종**(`tax_type_cd` 01~07). 3종이 아니다 | §4.2 |
| 약관 | **이용허락범위 제한 없음** — 저장·표시·상업적 이용 가능 | §5 |
| 한도 | 1회 **100건** / 1일 **100만건**(개발계정) | §6 |
| 신선도 | 30분 주기 동기화. 신규 개업자 **1~2일** | §6 |

**설계를 가르는 세 가지.**

1. **`/validate` 는 일치할 때만 `/status` 의 응답을 품는다.** 진위확인이 성공(`valid=01`)하면 진위 + 휴폐업 + 과세유형을 한 호출로 얻는다. 그러나 **불일치(`valid=02`)면 `status` 키가 아예 오지 않는다**(실측) — 그때는 상태를 따로 조회해야 한다. 즉 "한 호출로 둘 다" 는 **성공 경로에만** 성립한다.
2. **`/status` 응답에 상호도 대표자명도 없다.** 이건 조회 API 가 아니라 **검증 API** 다. 「발급 불가 거래처」의 결측 상호·대표자명을 국세청에서 **채울 수 없다** — 사람이 채워야 한다는 [KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §7.5 의 전제가 그대로 유지된다.
3. **개인정보가 응답이 아니라 요청에 있다.** `/validate` 는 대표자성명을 국세청으로 **보내는** API 다. `/status` 만 쓰면 개인정보 처리가 사실상 발생하지 않는다.

## 2. 엔드포인트와 인증

| | 진위확인 | 상태조회 |
|---|---|---|
| `operationId` | `validate` | `status` |
| 메서드·경로 | `POST /validate` | `POST /status` |
| Content-Type | `application/json` | `application/json` |
| 요청 바디 | `{"businesses": [BusinessDescription, …]}` | `{"b_no": ["0000000000", …]}` |
| 응답 | `ValidationApiResponse` | `StatusApiResponse` |

Swagger 원문: *"`GET` METHOD가 아닌 `POST` METHOD 로만 제공됩니다."* · *"`serviceKey` 및 `returnType` 은 URL 에 querystring 으로 넣어주셔야 합니다."* · *"그 외 `b_no` 등의 JSON string은 반드시 `body`로 넣어 호출해주세요."*

인증은 `securityDefinitions` 에 두 벌이 선언돼 있고 **OR 관계**다.

```json
"query_key":  { "type": "apiKey", "name": "serviceKey",    "in": "query"  }
"header_key": { "type": "apiKey", "name": "Authorization", "in": "header" }
```

> ⚠ `returnType` 은 `info.description` **산문에만** 있고 `parameters` 에 선언돼 있지 않다. Swagger codegen 으로 클라이언트를 만들면 이 파라미터가 **빠진다.** 손으로 붙여야 한다. 생략하면 JSON 이 기본이다.

## 3. 요청

### 3.1 `BusinessDescription` — 진위확인 요청 항목

`required: ["b_no", "start_dt", "p_nm"]`

| 필드 | 필수 | 의미 | 입력 규칙 (Swagger 원문) |
|---|:-:|---|---|
| `b_no` | ✅ | 사업자등록번호 | **숫자 10자리만.** `-` 등 기호 제거 |
| `start_dt` | ✅ | **개업일자** | **YYYYMMDD.** 기호 제거. **사업자등록증에 표기된 개업연월일** |
| `p_nm` | ✅ | 대표자성명1 | 외국인 사업자는 **영문명** |
| `p_nm2` | | 대표자성명2 | 외국인 사업자의 **한글명칭만**. 공동대표자명이 아니다 |
| `b_nm` | | 상호 | `(주)`·`주식회사`·`（주）` 위치 무관, 앞뒤 공백 무시 |
| `corp_no` | | 법인등록번호 | **숫자 13자리만** |
| `b_sector` | | 주업태명 | 모든 공백 무시 (`'서 비 스'` ≡ `'서비스'`) |
| `b_type` | | 주종목명 | 모든 공백 무시 |
| `b_adr` | | 사업장주소 | 모든 공백 무시. **v1.1 에서 추가** |

> ⚠ **`p_nm2` 는 외국인 사업자가 아니면 넣으면 안 된다.** Swagger 원문: *"외국인 사업자가 아닌 경우 이 항목/값을 추가하면 진위확인이 되지 않음"*. 빈 값으로라도 키를 넣는 것과 아예 넣지 않는 것이 다르다.
>
> 반대로 **필수가 아닌 항목을 빈값으로 검색해야 하면 `""` 로 JSON 에 포함**해야 한다(원문). 키 유무와 빈 문자열이 서로 다른 의미를 갖는 API 다.

**주업종코드는 없다.** 업종 관련 필드는 `b_sector`(주업태명)·`b_type`(주종목명) 둘뿐이고 **명칭 문자열**이지 코드가 아니다. [ONT-CLS-001](../ontology/ONT-CLS-001_korean_industry_code_systems.md) 의 국세청 업종코드와 연결되지 않는다.

### 3.2 `setive_` 필드와의 대응

| API 필드 | 우리 필드 | 비고 |
|---|---|---|
| `b_no` | 코어 `tax_id` | `identifiers.normalize_brn` 으로 숫자 10자리 |
| `start_dt` | `setive_biz_open_date` | Date → `YYYYMMDD` 문자열 변환 필요 |
| `p_nm` | `setive_ceo_name` | |
| `b_nm` | 코어 `customer_name`/`supplier_name`/`company_name` | |
| `corp_no` | `setive_corp_reg_no` | `normalize_crn` |
| `b_sector` | `setive_biz_type` (업태) | |
| `b_type` | `setive_biz_class` (종목) | |
| `b_adr` | `Address` DocType 평탄화 | 필드로 복제하지 않는다 |

> 진위확인이 `p_nm`(대표자성명)을 **required** 로 요구한다. 이것은 **세법상 필요적 기재사항 논의와 별개 층위**다 — 부가세법 제32조① 은 공급받는자 측에 등록번호만 요구한다([ONT-ENT-002](../ontology/ONT-ENT-002_korean_tax_party_and_transaction_axes.md) §2.5). 즉 대표자성명이 비어도 **세법상 문제는 아니지만 이 API 를 호출할 수는 없다.** `setive_ceo_name` 에 `reqd` 를 걸지 않는 결정([KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §7.4)은 유지하되, 「발급 불가 거래처」 리포트가 **「진위확인 불가 거래처」** 도 함께 집어낸다.

## 4. 응답

### 4.1 `BusinessStatus` — 11필드. 두 엔드포인트가 공유한다

`/status` 의 `data[]` 와 `/validate` 의 `data[].status` 가 **동일한 `$ref`** 다.

| 필드 | 의미 | 값 |
|---|---|---|
| `b_no` | 사업자등록번호 | |
| `b_stt` | 납세자상태 **명칭** | `계속사업자` · `휴업자` · `폐업자` |
| `b_stt_cd` | 납세자상태 **코드** | `01` · `02` · `03` |
| `tax_type` | 과세유형 **명칭** | §4.2 |
| `tax_type_cd` | 과세유형 **코드** | `01`~`07` |
| `end_dt` | 폐업일 | YYYYMMDD |
| **`utcc_yn`** | **단위과세전환폐업여부** | `Y` · `N` — §4.3 |
| `tax_type_change_dt` | 과세유형 전환일자 | YYYYMMDD |
| `invoice_apply_dt` | 세금계산서적용일자 | YYYYMMDD |
| `rbf_tax_type` | 직전 과세유형 명칭 | |
| `rbf_tax_type_cd` | 직전 과세유형 코드 | `01` · `02` · `07` · `99`(해당없음) |

`/validate` 는 여기에 `valid`(`01` Valid / `02` Invalid) · `valid_msg` · `request_param`(요청 에코백) 을 더한다.

**미등록 사업자번호의 실제 응답** (실측) — `tax_type` 에만 메시지가 오고 **나머지 필드는 전부 빈 문자열**이다.

```json
{ "b_no": "1234567890", "b_stt": "", "b_stt_cd": "",
  "tax_type": "국세청에 등록되지 않은 사업자등록번호입니다.", "tax_type_cd": "",
  "end_dt": "", "utcc_yn": "", "tax_type_change_dt": "",
  "invoice_apply_dt": "", "rbf_tax_type": "", "rbf_tax_type_cd": "" }
```

최상위는 `{request_cnt, match_cnt, status_code, data[]}` 다. **`match_cnt` 는 요청 중 국세청에 등록된 건수**다 — 위 예시는 3건 요청에 `match_cnt: 2`.

> ⚠ **미등록 판별을 문자열 매칭으로 하지 않는다.** 실물 문자열에는 Swagger description 과 달리 **마침표가 붙어 있다**(`…입니다.`). 문구가 바뀌면 조용히 깨진다.
> 대신 **`b_stt_cd` 가 빈 문자열인가**로 판별하고, 총계는 `match_cnt < request_cnt` 로 교차 확인한다. 둘 다 구조적 신호라 문구 변경에 영향받지 않는다.

> **응답에 `checked_on` 은 없다.** 관측 시각은 **우리가 붙이는 메타데이터**다([ONT-ENT-002](../ontology/ONT-ENT-002_korean_tax_party_and_transaction_axes.md) §2.2 가 요구하는 `checked_on` 이 그것). `b_stt_dt`·`open_dt` 도 없다.

### 4.2 과세유형은 **7종**이다

| 코드 | 명칭 (원문) |
|---|---|
| `01` | 부가가치세 일반과세자 |
| `02` | 부가가치세 간이과세자 |
| `03` | 부가가치세 과세특례자 |
| `04` | 부가가치세 면세사업자 |
| `05` | 수익사업을 영위하지 않는 비영리법인이거나 고유번호가 부여된 단체, 국가기관 등 |
| `06` | 고유번호가 부여된 단체 |
| **`07`** | **부가가치세 간이과세자(세금계산서 발급사업자)** |

> ⚠ **`07` 이 이 표에서 가장 중요하다.** 간이과세자이면서 **세금계산서를 발급해야 하는** 유형이다. "간이과세자 = 발급 불가" 로직을 박으면 07 거래처에 **미발급 사고**가 난다(가산세 2%). 반대로 02 에 발급하면 오발행이다. 둘을 반드시 구분한다.
>
> `invoice_apply_dt`(세금계산서적용일자)가 07 유형의 **발급 개시일**이며, 그 이전 공급분은 발급 대상이 아니다.

**미등록·삭제된 사업자등록번호는 `b_stt_cd` 가 아니라 `tax_type` 문자열로 온다.**

| | Swagger description | **실물 (실측)** |
|---|---|---|
| `/status` `tax_type` | `국세청에 등록되지 않은 사업자등록번호입니다` | `국세청에 등록되지 않은 사업자등록번호입니다**.**` |
| `/validate` `valid_msg` | `확인할 수 없습니다` | `확인할 수 없습니다**.**` |

> ⚠ **실물에는 마침표가 있고 Swagger 문서에는 없다.** 문서 문자열을 그대로 복사해 `==` 비교하면 **영구히 매칭 실패**한다. 애초에 문자열 매칭을 쓰지 말고 §4.1 의 구조적 신호(`b_stt_cd == ""`, `match_cnt`)를 쓴다.

### 4.3 `utcc_yn` — 폐업 판정을 뒤집는 필드

**`b_stt_cd = 03`(폐업) 이면서 `utcc_yn = Y` 이면 실제 폐업이 아니다.** 사업자단위과세 전환에 따른 **형식적 폐업**이며 사업자는 정상 영업 중이다.

이 조건을 빼면 정상 거래처가 폐업자로 경고되고, **`end_dt` 비교로도 걸러지지 않는다** — 전환일이 폐업일로 들어오므로 과거 공급분만 정상 판정되고 현재·미래 거래가 전부 오탐이다.

```
폐업 경고 =  b_stt_cd == "03"
          ∧  utcc_yn != "Y"
          ∧  공급시기 > end_dt
```

세 조건이 모두 필요하다. 폐업자 수취분도 **폐업일 이전 공급분은 정상 공제**된다([KB-KOR-005](./KB-KOR-005_localization_roadmap.md) §4.2).

### 4.4 오류

| `status_code` | 조건 | HTTP |
|---|---|---|
| `OK` | 정상 | 200 |
| `TOO_LARGE_REQUEST` | 100건 초과 | 413 |
| `BAD_JSON_REQUEST` | JSON 파싱 실패 | 400 |
| `REQUEST_DATA_MALFORMED` | 필수 파라미터 누락 | 400 |
| `INTERNAL_ERROR` · `HTTP_ERROR` | 서버 오류 | 500 |

Swagger 원문: *"에러 종류에 따라 status code가 400, 411, 413, 500 으로 반환되며, 에러 발생시에도 response에 오류 메세지가 return됩니다."*

**인증 실패의 실제 응답** (실측) — `status_code` 봉투가 **아니다.** 별개 형식이다.

```
HTTP 401   {"code": -4, "msg": "등록되지 않은 인증키 입니다."}
```

> ⚠ 웹에 흔한 `OpenAPI_ServiceResponse` / `cmmMsgHeader` / `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` 봉투는 **`apis.data.go.kr` 계열의 포맷이고 이 호스트는 쓰지 않는다.** 그 문자열을 찾는 코드를 쓰면 인증 오류를 못 잡는다.

**한도 초과의 실제 응답** (실측) — `data` 없이 `status_code` 만 온다.

```
HTTP 413   {"status_code": "TOO_LARGE_REQUEST"}
```

> **운영 코드는 두 층으로 검사한다.** ① HTTP 상태가 200 인가 ② 바디에 `status_code == "OK"` 가 있는가. 인증 실패는 `status_code` 키 자체가 없으므로 `body.get("status_code")` 만 보면 `None` 을 정상으로 오판할 수 있다. 그 외 응답은 **바디 원문을 그대로 로그에 남긴다.**

## 5. 약관 — 저장·표시·상업적 이용이 가능하다

| 질문 | 답 | 근거 |
|---|---|---|
| DB 저장 | **가능** | 이용허락범위 **"제한 없음"**. 저장·캐시 금지 문구 부재 |
| 화면 표시 | **가능** | 〃 |
| 가공·변형 | **가능** | 공공누리 3·4유형(변형금지) 미적용 |
| 상업적 이용 (SaaS ERP 탑재) | **가능** | 공공데이터법 제3조 — 공공기관은 영리적 이용도 허용하여야 한다 |
| 출처표시 의무 | **없음** | 공공누리 유형 **미부착**. 1~4유형이 아니므로 의무 없음 (관례상 표기는 권장) |

`data.go.kr` 는 저작물성 있는 데이터에 공공누리 제0~4유형을 부착하는데, 이 데이터셋에는 유형 대신 **"이용허락범위 제한 없음"** 이 붙어 있다.

> 🔴 **면책 조항이 설계를 제약한다.** 이용정책 원문: *"제공기관은 공공데이터의 제공과 관련하여 공공데이터의 품질, 공공데이터의 제공중단 등으로 손해 발생 시 책임을 지지 않습니다."*
> → 국세청 응답을 근거로 한 거래 판단의 책임은 **전적으로 우리 쪽**이다. **"국세청 확인필" 같은 보증성 UI 문구를 쓰지 않는다.** 대신 **조회 시각(as-of)을 반드시 함께 저장·표시**한다 — `Korea Party Tax Status.checked_on` 이 그 자리다.

**키 공유 금지** — 이용약관상 회원은 인증정보를 타인과 공유할 수 없다. 멀티테넌트에서 SETIVE 공통 키를 전 테넌트가 쓰는 구조가 이 조항에 걸리는지는 **미확인**이며, [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) §4.2 가 이미 "테넌트별 키를 기본, 공통 키는 옵트인 폴백" 으로 정한 방향과 같다.

### 5.1 개인정보 — 비대칭에 주의한다

| 구간 | 개인정보 | 비고 |
|---|:-:|---|
| `/validate` **요청** `p_nm`·`p_nm2` | ✅ | 우리가 국세청으로 **내보내는** 값 |
| `/validate` **응답** `request_param` | ✅ | 요청을 그대로 에코백 — 응답에 성명이 다시 담긴다 |
| `/status` 요청·응답 | ❌ | `b_no` 만 보내고 성명·상호는 오지 않는다 |

**이 API 는 개인정보를 주는 API 가 아니라 받는 API 다.** 설계 권고:

1. **`/status` 를 기본 경로로 둔다.** 휴폐업·과세유형만 필요하면 성명을 아예 처리하지 않는다.
2. `/validate` 는 최초 등록 시 1회만 호출하고 **응답의 `request_param` 을 저장하지 않는다.** 저장할 값은 `valid`(01/02) + 검증 시각뿐이다.

> 개인정보보호법 조문 해석은 1차 출처로 확인하지 않았다 — **법률 검토 항목**(§9).

## 6. 운영 — 한도·신선도·serviceKey

| 항목 | 값 | 근거 |
|---|---|---|
| 1회 배열 길이 | **100건** 초과 시 `TOO_LARGE_REQUEST`/413 | Swagger |
| 1일 호출 | **개발계정 1,000,000건** | 포털 메타 |
| 심의 | 개발·운영 **양 단계 자동승인** | 포털 메타 |
| 운영계정 전환 후 한도 | **미확인** — 공시되지 않음 | §9 |
| 데이터 동기화 | **30분 주기** | 포털 메타 |
| 신규 개업자 반영 | **1~2일** | 포털 메타 |
| 비용 | 무료 | 포털 메타 |

> **개발계정만으로 이미 일 100만건이다.** 웹에 흔한 "개발 1,000건 / 운영 10만건" 은 포털 **일반 기본값**이고 이 데이터셋에는 해당하지 않는다. 따라서 **운영계정 전환을 M4 의 선행 과제로 잡을 필요가 없다.** 진짜 병목은 **1회 100건 배치 상한**이며, 기존 거래처 일괄 검증 시 청크 처리가 필요하다.

### 6.1 serviceKey 인코딩 — 가장 많이 깨지는 곳

포털은 같은 키를 **Encoding / Decoding** 두 형태로 준다. 원본 키에 Base64 잔재 `+`·`/`·`=` 가 들어가기 때문이다.

**규칙: 퍼센트 인코딩은 정확히 한 번만 적용되어야 한다.**

| 방식 | 키 | 결과 |
|---|---|---|
| ✅ `params={"serviceKey": KEY}` | **Decoding 키** | 클라이언트가 `+` → `%2B` 로 1회 인코딩 |
| ✅ URL 문자열 직접 조립 | **Encoding 키** | 이미 인코딩된 값을 그대로 전달 |
| ❌ `params=` 에 **Encoding 키** | | `%` 가 `%25` 로 **이중 인코딩** |
| ❌ 조립 URL 에 **Decoding 키** | | 쿼리의 `+` 가 **공백**으로 해석됨 |

**가장 안전한 방법 — 어느 형태를 받았는지 따지지 않고 `unquote` 로 정규화한다.** 실측으로 확인했다.

```python
import urllib.parse, requests

# 받은 키가 Encoding 이든 Decoding 이든 항상 Decoding 형태로 맞춘다.
#   Decoding 키의 문자집합은 base64(A-Za-z0-9+/=) 라 '%' 가 없다 → unquote 는 무연산.
#   '+' 를 공백으로 바꾸는 것은 unquote_plus 지 unquote 가 아니다 → 훼손되지 않는다.
key = urllib.parse.unquote(raw_key)

resp = requests.post(
    "https://api.odcloud.kr/api/nts-businessman/v1/status",
    params={"serviceKey": key, "returnType": "JSON"},   # 여기서 1회 인코딩된다
    json={"b_no": ["0000000000"]},
    timeout=15,
)
```

> 이 정규화가 실제로 필요했다. 2026-09-17 검증에서 포털이 준 키는 **Encoding 형태**(98자, `%` 5개)였고 그대로 `params=` 에 넣으니 `%` 가 `%25` 로 이중 인코딩되어 **전 호출이 `HTTP 401 {"code":-4}`** 였다. `unquote` 로 88자 Decoding 형태로 바꾸자 전부 통과했다. `scripts/nts/probe.py` 의 `load_key()` 가 이 처리를 하며 어느 형태를 받았는지 출력에 찍는다.

> ⚠ 키 발급 직후 **1시간 내**에는 정상 키도 인증 오류가 날 수 있다. 해당 API 를 **활용신청하지 않은** 경우에도 같은 오류로 보인다.
> ⚠ `httpx` 는 쿼리 인코딩에서 `+` 를 safe 문자로 둘 수 있어 `requests` 와 다르게 동작할 소지가 있다(**미확인**). 첫 배포 전에 실제 응답으로 1회 검증한다.

### 6.2 캐시와 재조회

- **30분 미만 캐시는 무의미하다**(원천 동기화 주기가 30분).
- 신규 개업자는 1~2일 공백이 있으므로 `valid=02` 를 **"확인 불가"** 로 표시하고 **"신규 개업 가능성 — 1~2일 후 재조회"** 를 분리 안내한다. **하드 블로킹하지 않는다**([KB-KOR-005](./KB-KOR-005_localization_roadmap.md) §4.2 의 결정과 같다).
- 조회는 부작용이 없으므로 재시도가 안전하다.

## 7. 이 API 가 **하지 못하는 것**

착수 전에 못박아 둔다. 기대를 잘못 걸면 M4 설계가 어긋난다.

| 기대 | 실제 |
|---|---|
| 상호·대표자명을 **받아와서** 결측을 채운다 | ❌ `/status` 응답에 **없다.** `/validate` 는 우리가 보낸 값을 에코백할 뿐 |
| 주소를 받아온다 | ❌ 없다 |
| 업태·종목을 받아온다 | ❌ 없다. 요청으로 **보낼** 수만 있다 |
| 주업종코드를 받아온다 | ❌ 없다 |
| 필드별로 무엇이 틀렸는지 알려준다 | ❌ `valid`=01/02 뿐. 어느 항목이 불일치인지 **알려주지 않는다** |
| 휴폐업·과세유형을 받아온다 | ✅ **이것만 된다** |

**「발급 불가 거래처」의 결측은 이 API 로 채울 수 없다.** 사람이 채운다는 [KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §7.5 의 전제가 유지된다. 이 API 의 역할은 **사람이 채운 값이 국세청 원장과 맞는지 확인**하는 것이다.

### 7.1 다른 무료 공공 API 로도 채울 수 없다 (2026-09-17 조사)

"그럼 다른 무료 API 로 상호·대표자명을 받아오면 되지 않나" 가 자연스러운 다음 질문이다. **답은 아니다.** 사업자등록번호를 키로 상호·대표자명을 돌려주는 무료 공공 API 는 **범용으로 존재하지 않는다.** 부분 커버리지만 있다.

| 경로 | 무료 | BRN 으로 조회 | 상호·대표자명 | 커버 범위 |
|---|:-:|:-:|---|---|
| 국세청 15081808 (이 문서) | ✅ | ✅ | ❌ **입력이지 출력이 아니다** | 전 사업자 |
| 공정위 통신판매사업자 (15126315) | ✅ | ✅ | 상호 ✅ / 대표자명 **미확인** | **통신판매업 신고자만** |
| DART OpenDART 기업개황 | ✅ | ❌ `corp_code` 키 | 둘 다 ✅ | **DART 공시대상회사만** |
| 금융위 기업기본정보 (15043184) | ✅ | ❌ 법인등록번호·기업명 키 | 대표자명 ✅ | 법인만 (비외감 58만건) |
| 민간 CB·스크래핑 (bizno·apick·CODEF 등) | ❌ 유료 | ✅ | ✅ | 광범위 |

**설계 결론 — 상호·대표자명은 "조회해 채우는 값" 이 아니라 "사람이 입력하고 국세청 API 로 검증하는 값" 이다.** 「발급 불가 거래처」 리포트가 **사람이 채우는 화면**이어야 하는 이유가 여기서 확정된다([KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §7.5). 자동 채움 기능을 기대하고 설계하면 전 거래처가 영구히 빈칸으로 남는다.

> 부분 커버리지를 쓰려면 **업종·법인군 한정**임을 UI 에 드러내야 한다. "공정위에서 못 찾았다" 가 "사업자가 아니다" 를 뜻하지 않는다 — 통신판매업 신고를 하지 않은 정상 사업자가 대다수다.

## 8. 이전 서술 정정

이 조사로 기존 KB 4종에서 오류를 찾았다. **아직 조회 연동 코드가 0줄이라 문서만 고치면 되는 시점**이다.

### 8-1. 2026-09-17 — 이 세션에서 고친 것

- **[KB-KOR-006](./KB-KOR-006_etax_invoice_integration.md):52 의 *"무료로 쓸 수 있는 국세청 API 는 … 정확히 1건"* 은 참이지만 표현이 부정확했습니다.** 유료 국세청 오픈API 가 따로 있어서 1건으로 줄어든 것이 아니라 **국세청 오픈API 자체가 1건**입니다(나머지 219건은 통계 파일데이터). "무료로 쓸 수 있는" 이라는 수식어가 아무 일도 하지 않아 읽는 사람이 "유료 것도 있나" 로 오해합니다. 실측 방법과 자기일관성 확인(219 + 1 = 헤더 총계 220)을 함께 적었습니다.

- **[ONT-ENT-002](../ontology/ONT-ENT-002_korean_tax_party_and_transaction_axes.md) §2.2 의 과세유형 `(일반 / 간이 / 면세)` 3종 열거는 불완전했습니다.** 국세청 축은 **7종**이며(§4.2), 특히 **`07` 부가가치세 간이과세자(세금계산서 발급사업자)** 가 빠져 있었습니다. 이 값이 없으면 "간이과세자 = 세금계산서 발급 불가" 라는 규칙이 구현에 박혀 07 거래처에 **미발급 사고**가 납니다. 7종 전체와 `tax_type` / `tax_type_cd`(명칭/코드 별도 필드) 구분을 반영했습니다.
- **`utcc_yn`(단위과세전환폐업여부) 의 존재를 어느 문서도 몰랐습니다.** `b_stt_cd=03` + `utcc_yn=Y` 는 **실제 폐업이 아니라** 사업자단위과세 전환에 따른 형식적 폐업입니다. [KB-KOR-005](./KB-KOR-005_localization_roadmap.md) §4.2 의 판정식(`b_stt_cd` + `end_dt` 비교)을 그대로 구현하면 **정상 영업 중인 거래처를 폐업자로 경고**하고, `end_dt` 비교로도 걸러지지 않습니다. 두 문서에 세 번째 조건을 추가했습니다(§4.3).
- **[KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) §7.4 의 `setive_tax_payer_type` Select 4종은 국세청 관측값과 대조가 불가능했습니다.** 선언값 축과 관측값 축의 값 집합이 다르면 "신고값 ≠ 관측값" 판정 자체가 성립하지 않습니다. 옵션을 `tax_type_cd` 01~07 에 1:1 대응시켰습니다.

### 8-2. 남은 정정 — 후속 세션 대상

아래는 **이 세션 범위 밖**이며 M4 착수 시 함께 반영한다. 위치를 명시해 둔다.

| 문서 | 위치 | 무엇을 고쳐야 하는가 |
|---|---|---|
| [KB-KOR-003](./KB-KOR-003_company_hook_tax_nts.md) | §7.5 | 리포트 컬럼에 `utcc_yn`·`tax_type_cd`·`rbf_tax_type_cd`·폐업일 추가. `utcc_yn` 없이는 폐업 컬럼이 오탐을 낸다 |
| [KB-KOR-008](./KB-KOR-008_etax_vendor_adapter_contract.md) | §3 | `Korea Party Tax Status` 가 `BusinessStatus` 11필드를 **원본 그대로** 저장한다는 점(파생 판정 전 원본 보존) |

둘 다 **조회 코드가 생겨야 의미가 있다.** 지금 컬럼만 만들면 영구히 빈칸이고, "원본 보존" 규칙도 저장하는 코드가 없으면 검증할 수 없다. 그래서 M4 구현과 같은 커밋에 넣는다.

이미 처리된 것 — ONT-ENT-002 §2.2(상태·과세유형 축 정정, 11필드 반영)와 KB-KOR-005 §4 M4 행("한 어댑터 한 호출")은 §8-1 에서 함께 고쳤다.

| 1 | 잘못된 키 | `401` `{"code":-4,"msg":"등록되지 않은 인증키 입니다."}` → §4.4 |
| 2 | `/status` 필드 집합 | Swagger 11필드와 **완전 일치** (초과 0 · 누락 0) |
| 3 | `utcc_yn` 실물 | 수신 확인 (`"N"`) |
| 4 | 미등록 번호 | 다른 필드 전부 빈 문자열, `match_cnt 2 / request_cnt 3` → §4.1 |
| 5 | 101건 요청 | `413` `{"status_code":"TOO_LARGE_REQUEST"}` → §4.4 |
| 6 | `/validate` 불일치 | `valid:"02"` + `valid_msg` + `request_param`. **`status` 키 없음** → §1 |

> `valid=01`(일치) 경로는 **미실측**이다. 실제 대표자성명·개업일자를 국세청에 보내야 하고
> 그것은 §5.1 이 "최초 등록 시 1회만" 으로 제한한 개인정보 전송이다. 테스트 목적으로
> 임의로 보내지 않았다. 일치 시 `status` 가 포함된다는 것은 Swagger `info.description`
> (*"일치할경우, valid: 01 및 해당하는 사업자 정보 return"*)에 근거한 **서술 기반**이다.

## 10. 알려진 한계

- **`valid=01`(진위확인 일치) 경로가 미실측이다.** 실제 대표자성명 전송이 필요해 하지 않았다. 일치 시 `status` 가 함께 오는지는 Swagger 서술에 근거한다. M4 착수 시 **테넌트 자기 회사 정보로** 1회 확인하는 것이 맞다 — 남의 대표자명을 테스트에 쓰지 않는다.
- **응답 지연·점검 시간대·간헐적 5xx 는 미확인이다.** 4종 호출이 전부 즉시 응답했을 뿐 부하·시간대별 거동은 모른다.
- **`httpx` 의 `+` 인코딩 거동은 여전히 미확인이다.** §6.1 의 `unquote` 정규화를 쓰면 `%` 가 사라져 이 쟁점 자체가 약해지지만, httpx 로 갈 거면 1회 확인한다.
- **운영계정 전환 후 트래픽 한도가 공시되지 않았다.** 개발계정 100만건으로 충분하다는 판단이라 당장 문제는 없다.
- **개인회원으로 상용 SaaS 에 탑재할 때의 추가 제약이 미확인이다.** 약관에 금지 문구는 없었으나, 키 소유주체와 서비스 운영주체를 일치시키는 편이 안전하다(담당자 이직 리스크). 사업자등록 후 **기업회원 + 프로젝트 서비스키** 전환을 권한다 — 강제는 아니다.
- **개인정보보호법상 대표자성명 처리근거를 1차 출처로 확인하지 않았다.** `/validate` 를 쓰기 전에 법률 검토가 필요하다. `/status` 만 쓰면 이 쟁점이 발생하지 않는다.
- **"이용허락범위 제한 없음" 의 공식 정의를 포털에서 서면으로 받지 않았다.** 감사 대응 근거가 필요하면 고객센터(1566-0025) 또는 국세청 기획조정관실(044-204-2370)에 서면 질의를 권한다.
- **서비스 중단 공지의 기계 판독 채널(RSS/API)이 없다.** 운영 시 회로차단기와 장애 시 수동검증 폴백을 전제로 설계한다.
- 필드별 최대 길이(`p_nm` 30자 등)는 제3자 문서에만 있고 **Swagger 원문에는 없다** — 인용하지 않았다.
