# ONT-ENT-002: 한국 세무 당사자·전표 분류 개념 모델

## 요약

한국 세무에서 하나의 거래를 서술하려면 **네 개의 독립한 축**이 필요하다. 이 넷을 하나로 뭉개면 반드시 깨진다.

```
   거래 = 당사자(누가) × 분류(무엇으로) × 시간(언제) × 식별자(어떻게 지목)
           §1~2          §3              §4          §5
```

특히 **시간**이 함정이다. "세금계산서 날짜"는 단일 값이 아니라 **공급시기 · 작성일자 · 발급일 · 전송일** 넷이며, 월합계 세금계산서에서는 이 셋이 전부 다르다. ERPNext 의 `posting_date` 는 이 넷 중 **어느 것도 아니다.**

---

## 1. 당사자 — 식별번호 체계

### 1.1 사업자 (Business Entity) — 사업자등록번호 BRN, 10자리

```
   1 2 3  -  4 5  -  6 7 8 9 0
   └─┬─┘     └┬┘     └──┬──┘ └ 검증번호
     │        │         └ 일련번호 4자리
     │        └ 사업자유형 구분코드 2자리
     └ 세무서 일련번호 3자리
```

**검증식** (실번호로 검산 확인):

```
   w = [1, 3, 7, 1, 3, 7, 1, 3, 5]
   S = Σ(d[i] × w[i])  for i in 0..8
       + (d[8] × 5) // 10        ← 9번째 자리는 ×5 후 몫을 추가 합산
   check = (10 − S % 10) % 10
```

**구분코드 해석표** (중간 2자리):

| 코드 | 의미 |
|---|---|
| 01~79 | 개인 과세사업자 |
| 80 | 법인 아닌 단체 · 다단계판매원 |
| 81 · 86 · 87 · 88 | 영리법인 **본점** |
| 82 | 비영리법인 |
| 83 | 국가·지방자치단체 |
| 84 | 외국법인 |
| 85 | 영리법인 **지점** |
| 89 | 법인 아닌 종교단체 |
| 90~99 | 개인 **면세**사업자 |

### 1.2 법인 (Corporation) ⊂ 사업자 — 법인등록번호 CRN, 13자리

```
   w = [1, 2] × 6
   S = Σ(d[i] × w[i])          ← 자릿수 분해 없이 그대로 합산
   check = (10 − S % 10) % 10
```

> **BRN 과 CRN 은 서로 독립된 식별자이며 변환 관계가 없다.**

### 1.3 개인 (Individual) — 주민등록번호 RRN, 13자리

**2020-10 이후 발급분은 종전 검증식이 성립하지 않는다.** 뒤 7자리 중 성별 1자리를 제외한 6자리가 임의번호로 바뀌었다.

→ 온톨로지에 **"검증 가능 구간"과 "검증 불가 구간"을 속성으로 남긴다.** 규칙을 무조건으로 기술하면 구현이 hard block 을 만든다.

> ⚠ 그렇다고 RRN 을 저장하지 않으면 안 된다. 전자세금계산서 `BusinessType.Code` 02 가 13자리를 실제로 요구하고, 매출처별 세금계산서합계표도 사업자등록번호 발급분과 주민등록번호 발급분을 **별도 행**으로 집계한다. 개인(비사업자) 대상 매출이 있는 사업자는 RRN 없이 발급이 불가능하다.

### 1.4 사업장 (Establishment) — 사업자에 1:N

종사업장번호 4자리로 식별한다.

> **부가세 신고 단위는 회사가 아니라 사업장이다.** 주사업장 총괄납부·사업자단위과세가 신고 단위를 바꾼다. "ERPNext Company 1개 = 사업장 1개" 가정은 성립하지 않을 수 있다.

## 2. 당사자 — 분류 · 상태 · 역할

### 2.1 분류

```
   사업자 ─classified_by→  업태 (Business Type)
                        →  종목 (Business Item)
                        →  주업종코드 (NTS Business Code)
```

[ONT-CLS-001](./ONT-CLS-001_korean_industry_code_systems.md) 의 미구현 항목 중 업태/종목·주업종코드가 여기서 값 단위로 채워진다. KSIC 세세분류·기준경비율·산재 사업종류와의 연결은 미수립 상태이며, **승격 경로(자유 Data → Link)를 관계로 기술**해 둔다.

### 2.2 상태 — 선언값이 아니라 관측값이다

```
   사업자 ─has_status→  사업자 상태  (계속 01 / 휴업 02 / 폐업 03)
                     →  과세유형     (일반 / 간이 / 면세)
                     →  과세유형 전환일 · 폐업일(end_dt)
```

이 상태는 사업자 본인이 아니라 **국세청이 부여하는 외부 사실**이며, **관측 시각(`checked_on`)과 함께여야 의미를 가진다.**

> ⚠ 폐업자에게 받은 세금계산서라도 **폐업일 이전 공급분은 정상 공제**된다. 상태 코드만 보고 판정하면 안 되고 `end_dt` 와 공급시기를 비교해야 한다. 신규 개업자는 국세청 반영에 1~2일 걸린다.

온톨로지에 **'관측값'과 '선언값'을 구분**해 둔다.

### 2.3 역할 — 위수탁은 3자 구조, 역발행은 아니다

```
   거래에서 사업자는  공급자 (Invoicer)
                   ·  공급받는자 (Invoicee)
                   ·  수탁사업자 (Broker)      ← 위수탁일 때만
```

| | 법적 지위 | XML | 인증서 |
|---|---|---|---|
| **위수탁** | 부가세법 시행령 **제69조의 법정 제도** | `BrokerParty` 섹션 별도 | **수탁자** 인증서로 서명 |
| **역발행** | 법정 제도가 아닌 **업무 절차** | 일반 세금계산서와 동일 | 공급자 인증서 |

> 이 구분을 개념 층에서 먼저 못박지 않으면 데이터 모델이 잘못 갈린다. 위수탁은 위탁판매·대리판매 관계를 전제하므로 **ERP SaaS 벤더가 고객 대신 발행하는 우회로가 될 수 없다.**

### 2.4 식별유형

```
   공급받는자 ─identified_by→  01 사업자등록번호
                            →  02 주민등록번호
                            →  03 외국인
```

**03 은 `ID` 에 `9999999999999` 고정값을 넣고 비고란에 실제 번호를 적는다.**

같은 축이 두 산출물(전자세금계산서 XML · 세금계산서합계표)에 쓰인다.

### 2.5 필요적 기재사항 ≠ XML 필수 항목 (혼동 주의)

| 층위 | 근거 | 공급받는자 측 요구 |
|---|---|---|
| **세법** | 부가세법 제32조① | **등록번호만** 필요적. 상호·대표자성명·업태·종목은 **임의적** 기재사항(시행령 제67조②) |
| **전자세금계산서 XML** | 국세청 표준 | 상호·대표자성명이 `1..1` |

> ⚠ 이 구분을 명시하지 않으면 **"대표자명 결측 = 매입세액 불공제"** 라는 잘못된 규칙이 구현에 박힌다. 둘은 별개 층위다.

## 3. 전표 분류 축

```
   거래 ─classified_by→  증빙유형  ×  과세유형  ×  고정자산매입 여부  ×  불공제 사유
```

| 축 | 값 |
|---|---|
| 증빙유형 | 세금계산서 / 매입자발행 / 신용카드·현금영수증 / 기타 / **계산서(면세)** |
| 과세유형 | 과세 / 영세율 / 면세 |
| 고정자산매입 | 여 / 부 |
| 불공제 사유 | 아래 8버킷 (별지 제22호서식) |

**네 축의 곱이 부가세 신고서 칸으로 사상된다.**

### 3.1 불공제 8버킷 — 셋은 전표 입력 시점의 선택지가 아니다

| # | 사유 | 판정 시점 |
|---|---|---|
| ① | 필요적 기재사항 누락 | **사후** (세무조사·신고 검토) |
| ② | 사업과 직접 관련 없는 지출 | 입력 시점 |
| ③ | 비영업용 소형승용차 | 입력 시점 |
| ④ | 기업업무추진비 및 이와 유사한 비용 | 입력 시점 |
| ⑤ | **면세사업등 관련** | **과세기간 말 안분 계산의 산출물** — 공통매입세액 × (면세공급가액 ÷ 총공급가액) |
| ⑥ | 토지의 자본적 지출 | 입력 시점 |
| ⑦ | 사업자등록 전 매입세액 | **자동 판정** (등록일 vs 거래일) |
| ⑧ | 금·구리 스크랩 거래계좌 미사용 | 입력 시점 |

> ⚠ 8버킷을 전부 전표 단위 Select 로 두면 실무와 어긋난다. **①⑤⑦ 은 별도 산출 경로로 분리**하고, 전표 Select 에는 ②③④⑥⑧만 둔다. ⑤는 별지 제22호서식의 2번 표(안분 계산 명세)에 연결된다.

### 3.2 매출 축은 파생 가능하고 매입 축은 파생되지 않는다

매출 측 일부(증빙유형·영세율 구분)는 전자세금계산서의 `Type.Code` 에서 파생할 수 있다. 그러나 **매입 측(불공제 8버킷·공통매입·고정자산매입)은 어디에서도 파생되지 않는다.** 별도로 수집해야 한다.

### 3.3 과세유형 분기 (설계에 반드시 남길 것)

| 유형 | 서식 | 신고 주기 | 특이사항 |
|---|---|---|---|
| 일반과세자 | 별지 제21호 | 법인 4회 / 개인 2회 | |
| **간이과세자** | **별지 제44호** | **연 1회 (익년 1/25)** | 직전연도 공급대가 4,800만원 미만이면 **세금계산서 발급 불가** |
| **면세사업자** | 부가세법 아님 | | **소득세법·법인세법**에 따라 **계산서** 발급 |

## 4. 시간 — 네 시각은 모두 다를 수 있다

```
   거래 ─has_time→  공급시기   (부가세법 제15·16·17조)
                 →  작성일자
                 →  발급일
                 →  전송일
```

**월합계 세금계산서**가 이 분리를 강제한다:

| 시각 | 값 |
|---|---|
| 공급시기 | 각 거래일 (N건) |
| 작성일자 | 그 달의 **말일** |
| 발급 | **익월 10일**까지 |
| 전송 | 발급일 **익일**까지 |

> **ERPNext `posting_date` 는 이 넷 중 어느 것도 아니다.** 시간 개념을 하나로 뭉개면 월합계에서 반드시 깨진다.

### 4.1 수정세금계산서 — 사유가 작성일자와 발급매수를 가른다

| 사유코드 | 작성일자 | 발급매수 |
|---|---|---|
| 01 기재사항 착오정정 | **당초** 작성일자 | 2장 |
| 02 공급가액 변동 | 사유 발생일 | 2장 |
| 03 환입 | 사유 발생일 | 음수 1장 |
| 04 계약 해제 | 사유 발생일 | 음수 1장 |
| 05 착오에 의한 이중발급 | 사유 발생일 | 2장 |
| 06 (당초 기재 착오) | **당초** 작성일자 | 음수 1장 |

> 수정발행은 **Credit Note 로 자동 판정할 수 없다.** 사유를 사용자에게 묻는 절차가 필수이며, **당초승인번호(`OriginalIssue.ID`) 연결이 끊기면 이후 대사와 합계표가 어긋난다.**

### 4.2 가산세 (공급자 귀속)

| 유형 | 요율 (공급가액 기준) |
|---|---|
| 미발급 | 2% |
| 지연발급 | 1% |
| 지연전송 | 0.3% |
| 미전송 | 0.5% |

## 5. 식별자 — 승인번호 24자리

```
   ┌──── 8 ────┬──── 8 ────┬──── 8 ────┐
   │ 작성일자   │ 국세청     │ 식별자     │
   │ YYYYMMDD  │ 등록번호   │            │
   └───────────┴─────┬─────┴───────────┘
                     │
        가운데 8자리 = 시스템사업자 등록번호
        앞 2자리가 발급 경로를 구분한다
```

| 앞 2자리 | 발급 경로 |
|---|---|
| 10 | 홈택스 |
| 20 | ARS |
| 41 | **ASP (발급대행사업자)** |
| 42 | ERP (표준인증 사업자) |
| 50 | 겸용서식 |
| 70 | 모바일 |
| 90 | 세무서 대리발급 |

> **이 구조가 "자체 발급 경로는 국세청 등록 없이 성립하지 않는다"는 아키텍처 제약의 근거다.** 승인번호 안에 발급 주체가 각인된다.

## 6. ERPNext 대응표

| 개념 | ERPNext 필드 | 대응 관계 |
|---|---|---|
| BRN | `Company.tax_id` · `Customer.tax_id` · `Supplier.tax_id` | 1:1. 단 **unique 도 reqd 도 아니다** |
| 업태 · 종목 | **없음** | 신설 필요 |
| 대표자성명 | **없음** | 신설 필요 |
| 고정자산매입 축 | `Item.is_fixed_asset` | 품목 → 전표 유도 |
| 과세유형 | `Item Tax Template` · `Tax Category` | **유도되지만 템플릿이 곧 축은 아니다** |
| 사업장 소재지 | `Address` (`pincode` = 국가기초구역번호 5자리) | |
| 공급시기 / 작성일자 / 발급일 / 전송일 | `posting_date` **하나뿐** | **1:4 불일치** — §4 |

> 개념과 필드가 1:1 이 아닌 지점을 **관계로 명시**한다. 특히 마지막 행이 이 문서의 핵심 경고다.

## 7. 알려진 한계

- **다사업장 모델이 미정이다.** 주사업장 총괄납부·사업자단위과세 사업자가 들어오면 사업장별 신고명세서와 본표 전용 칸 때문에 축 설계를 다시 손대야 한다.
- 별지 제21호서식은 **2025-07-04 개정**으로 칸 번호가 밀렸다((16)/(48) → (17)/(53)). **칸 번호를 코드에 상수로 박지 않는다** — 데이터 파일 + 개정 표식(`schema_version`)으로 분리한다.
- 업태·종목이 **자유 문자열**이다. KSIC·국세청 업종코드와의 연결은 [ONT-CLS-001](./ONT-CLS-001_korean_industry_code_systems.md) 의 미구현 항목으로 남아 있다.
- 전자세금계산서 XML 의 전체 항목 매핑표(`ExchangedDocument` · `TaxInvoiceDocument` · `InvoicerParty` · `InvoiceeParty` · `TaxInvoiceTradeLineItem`)는 **작성되지 않았다.** 필수 여부·자릿수·반복 횟수를 포함한 초안이 구현 착수 전에 필요하다.
- **비고란 3회 반복 제약**, 품목 라인 수 상한 등 XML 스키마 제약이 수집되지 않았다.
